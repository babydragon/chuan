# 申请宿主权限（capability-request）

> 什么时候读这一页：`host` / `hostd` 返回 `permission denied (host_path|host_argv|host_root)`，
> 或者你已经连续两次因为"看不见 / 不能跑"而换写法。
> 一旦决定申请，就**不要再试别的绕法**——那是在审批之下偷偷扩大动作面。

## 硬规则（五条，别商量）

1. **先 `capability(list)` 再申请**。已经覆盖的东西不申请；重复申请说明你在猜。
2. **一次只申请一类**（路径 / argv / root 分开写）。混在一起，人没法判断风险。
3. **同一个失败只申请一次**。同一个动作失败两次 → 停下来写单子。
4. **申请后停下**。单子发出即结束这一轮。不要"顺手把能做的部分先做了"来制造既成事实。
5. **改完自验**。按第 8 节跑验证；失败就如实报告，不要接着申请"加宽一点"。

## 流程

```
capability(list)                      # 现在能用什么
  ↓ 确实缺
capability(check, kind, item, mode)   # 已有就不申请
  ↓ 确实没有
capability(request, …8 节…)           # 写草稿 + 通知主人
  ↓ 停下，等主人改配置文件
（主人改完，热加载生效，不用重启）
  ↓
按第 8 节自验 → 失败如实报告
```

## 8 节怎么写

| 节 | 字段 | 写什么 | 反例 |
|---|---|---|---|
| 1 现场 | `scene` | 哪次工具调用、返回的完整错误、当时想做什么 | "权限不足" |
| 2 最小请求 | `request` | **一行 TOML**，精确到目录或 argv 前缀 | "需要访问 /var" |
| 3 必要性 | `necessity` | 现有能力为什么不够；试过哪三条路 | "看起来需要" |
| 4 可见范围 | `visibility` | 读什么、写什么、会不会看到别的用户数据 | 留空 |
| 5 更小的选项 | `alternatives` | 能否只给单个文件 / 只读 / 只一次 | "没有更小的" |
| 6 副作用 | `risk` | 误用会怎样；可不可逆 | "应该没事" |
| 7 回滚 | `rollback` | 撤销那一行之后回到什么状态 | 留空 |
| 8 自验 | `verify` | 贴完配置后跑的具体命令 + 期望输出 | "再试一次" |

第 5 节是刻意加的：先回答"能不能更小"，大多数申请会自己缩到单个文件。

## 三种 kind

- `host_path`：加一个可见目录（`[host.path]`）。默认 `ro`；`rw` 只有主人能决定。
- `host_argv`：提权命令前缀（`[[host_elevated.grant]]`）。**不能申请 `always`**。
- `host_root`：声明"这件事没 root 做不了"。同样只能由主人写进表。

## 什么不要申请

- 把 `/` 或 `/run` 整块挂进来（配置解析会直接报错）。
- 把 `/etc/chuan/secrets`、`services.d`、`chuan.toml` 加进可见范围——这三条是写死的遮蔽项。
- 用 `exec`（沙盒）反复猜路径。沙盒里本来就看不到宿主，猜不到是设计使然。
