# 长期记忆的筛选（设计，未实现）

> 现状：facts **全量注入**（`[memory] inject_limit`，默认 1000）。
> 本文只描述"超过上限时怎么挑"，**代码还没写**。

---

## 0. 先明确它要解决什么

- **不是**为了"更准"：全量注入的召回是 100%。只要 facts 在几百条量级，全量就是最优解。
- **是**为了**削峰**：facts 涨到几千条时，system 前缀会变得又长又贵（首字变慢、冷启变贵）。
  这时需要一个"取相关子集"的算法，且**不能像旧代码那样在普通问题上把记忆清空**。

判断标准：**宁可多带几条无关的，也不能漏掉相关的那一条。**

---

## 1. 为什么不能直接用 FTS

| 问题 | 原因 |
|---|---|
| 查询是整句 | FTS 把整句当一个 phrase，要求连续命中 |
| 中文关键词多为 2 字 | trigram 分词要求 ≥3 字才能 MATCH；2 字只能 LIKE |
| 方向不对 | 我们问的是"事实里有没有提到这个问题"，而不是"文档里有没有这句话" |

所以筛选在**内存里**做：facts 本来就已经取出来了（≤ `inject_limit`），不需要再查一次库。

---

## 2. 算法

### 2.1 归一化

- 全角 → 半角；ASCII 转小写；
- 去掉标点、空白；
- ASCII 连续串（`HP M15`、`Brave`）按**整词**处理；
- CJK 连续串按 **2-gram**（中文在无词典下的最小可靠单位）。

### 2.2 事实侧特征与权重

```
fact = (subject, predicate, value)
w(field): subject 3 · predicate 2 · value 1
```

理由：人问"女儿班级是什么"时，问的是**键**；value 是答案，不该和键同权。

### 2.3 IDF（在当前 fact 语料上算）

```
idf(g) = ln(1 + N / (1 + df(g)))
```

- `df(g)`：包含该 gram 的 fact 条数；
- 作用：把"什么/怎么/我的"这类不区分度的 gram 压到接近 0。

### 2.4 打分

```
score(f) = Σ_{g∈grams(f)} w(g)·idf(g)·[g ∈ grams(q)]
           ─────────────────────────────────────────
           Σ_{g∈grams(f)} w(g)·idf(g)          ← 事实被问题覆盖的比例

qcov(f)  = |grams(q) ∩ grams(f)| / |grams(q)|   ← 问题被事实解释的比例

rank = 0.7·score + 0.3·qcov
```

`qcov` 防的是"一条超长 fact 靠一两个词刷分"。

### 2.5 停用词（只过滤查询侧）

```
什么 怎么 多少 我们 你们 他们 一下 现在 可以 请问 知道 记得 告诉 帮我
的是 了吗 呢啊 这个 那个 哪个 有没有 时候 一个 不是 就是
```

30–50 个足够；不做词表工程。

### 2.6 门槛与兜底

- 候选：`score ≥ 0.12` 且至少命中一个 `idf > 中位数` 的 gram；
- **永远带上最近 30 条**（人对"最近说过什么"的预期最强）；
- 最终 = 最近 30 + top-N（N=50），按 id 去重；
- 排序只在"超出上限"时使用，**不改变注入顺序**（仍按 `valid_from DESC`），避免每轮前缀抖动。

## 3. 代码落点

```rust
// crates/harness-kernel/src/fact_rank.rs（新文件，纯函数）
pub fn rank_facts(query: &str, facts: &[Doc], k: usize) -> Vec<DocId>;
```

调用点（`actor.rs` 的 facts 注入处）：

```rust
let limit = self.cfg.memory_inject_limit.max(1);
let q = DocQuery { scopes, kinds, limit };
if let Ok(docs) = rd.list_docs(q).await {
    let docs = if docs.len() < limit { docs }          // 没超限：全量
               else { recent30(&docs) + rank_facts(query, &docs, 50) };
    // 注入
}
```

- 不需要新查询、不碰 store/FTS；
- 复杂度：1000 条 × ~30 gram ≈ 3 万次 HashSet 查询，**<1 ms**。

---

## 4. 怎么验证"够准"

用固定 fixture（**不含真实数据**）：30 条通用 facts + 12 个问题，每个标注应命中的 1–2 条。

- `recall@5 ≥ 0.9`、`precision@5 ≥ 0.6`（字面匹配的上限大致如此）；
- 另加两个**预期失败**的用例并写进注释：
  - 同义词（问"女儿"，事实写"孩子"）；
  - 指代（"上周记的那条"）。

---

## 5. 已知局限

1. **同义词无解**：`女儿` / `孩子` 是两个 gram；
2. **指代无解**：没有字面锚点；
3. **长 value 稀释**：value 很长时覆盖比例天然低（靠字段权重与 `qcov` 缓解）；
4. **不处理否定**："不是那个"与"是那个"同分。

结论：**默认全量注入**；本算法只在超限时兜底。真要提升语义召回，只有两条路——扩展同义词表（数据），或上向量（已否决）。

---

## 6. 触发条件

- facts 稳定超过 `inject_limit`（默认 1000）**且**观察到"重要旧记忆问不到"；
- 或者需要压低冷启动成本（system 前缀过长导致首字明显变慢）。

在触发之前，保持现状：全量注入 + 上限截断。
