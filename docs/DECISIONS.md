# 关键决策记录（ADR）

> 每条记录：**决定 · 理由 · 代价 · 反悔成本**。被推翻的决定保留在 §13，说明推翻了什么。
> 术语以 `GLOSSARY.md` 为准。

---

## D1 · 语言与部署形态：Rust 单二进制

**决定**：Rust 单二进制 + systemd，跑在目标板本地；不引入 Node/容器编排。
**理由**：目标机 riscv64；单二进制便于交叉编译与部署；无中间件运维。
**代价**：生态比 TS 弱，需要自己写不少编排代码。
**反悔成本**：高（等于重写）。
**备选**：Pi/Node 方案（曾设计为 v0.2，因运行时要求被否决，见 §13）。

---

## D2 · LLM 层自写，接口冻结为 `TurnDriver`

**决定**：自写 OpenAI 兼容客户端（约 400 行）+ 自己的 turn 状态机；不依赖 rig 的 `AgentRun`。
**理由**：① journal-first 决定了 loop 必须归我们；② rig 的 `AgentRun` 只能在轮边界重建、重建后计数器归零、修复产物（synthetic 消息）仍需自己入账；③ rig wire 层每两周一次破坏性变更（12 个月 22 个 minor、167 条 breaking）；④ 另两个候选各有硬伤（`async-openai` 丢 `reasoning_content`；`openai-api-rs` 流式 tool-call 丢分片）。
**代价**：约 400 行协议代码；方言差异要自己处理。
**反悔成本**：低——`TurnDriver` 是 trait，可把 rig wire 层作为第二实现接入。
**失败条件**：若自写客户端在三种 provider 上都无法稳定解析，再切 rig。

---

## D3 · Journal 是唯一真相

**决定**：持久化只信任 journal（消息、工具调用、任务、审批）；不持久化任何框架的内存状态。
**理由**：框架状态含 opaque reasoning、cache 标记、provider 元数据；升级或换 provider 即废。日志是 provider 无关、可审计、可重放的。
**代价**：需要自己实现恢复；journal 要含 `synthetic` 种类以保存模型插入的纠正性内容。
**反悔成本**：低（只是"多存一层"的反方向）。
**验收**：任一崩溃点恢复后，不产生重复的工具副作用；`synthetic(repair)` 事件不会因恢复而重复生成（历史中本就存在的非法调用除外）。

---

## D4 · 恢复按崩溃点分级 + 副作用三级

**决定**：不追求逐 token 续写；按"用户消息/流式中/工具未执行/工具执行中/终稿未送达"分别处理；副作用分 `Pure`/`Idempotent(key)`/`External`。
**理由**：重放整个 turn 会重复副作用；家庭场景重发一条消息的代价远低于重复打印。
**代价**：交互 turn 是 at-most-once，极端情况下用户可能看到"重发"提示。
**反悔成本**：低（可在 `External` 上放宽为"至少一次 + 去重按钮"，已实现）。

---

## D5 · 授权轴是能力越界，不是命令黑名单

**决定**：按**执行域**审批——`sandbox`（免审批）/ `self_modify`（问）/ `outbound`（域名白名单即授权）/ `host_exec`（默认拒绝），见 `[policy]`。黑名单只作快速失败提示，不作为安全边界。
**理由**：沙盒已是边界（`/usr` 只读、`/home` 不可见、无网、cgroup 硬限），命令名不决定后果；按命令审批会训练橡皮图章。工具只是入口，真正要判的是"有没有出沙盒"。
**代价**：依赖沙盒可用性；沙盒降级时必须自动收紧为命令白名单 + 全审批。出网的闸从"逐次确认"挪到"域名白名单"，白名单过宽等于放开外泄通道。
内网调试（`lan`）是例外：bwrap 只能整块隔离或放开网络，无法"只通内网"，因此该 lane 保留网卡但**看不到任何宿主文件与凭据**，
并逐条审批；网上导入的技能跑在离线的 `exec` 里，结构上够不到它。
**反悔成本**：低（策略是配置）。

---

## D6 · 技能是纯函数，且权限不可自授

**决定**：技能只读写 workspace；`SKILL.md` 正文永不进上下文（只注入结构化 manifest）；`network` 等权限由策略层授予，不由技能声明。
**理由**：`SKILL.md` 由模型自己生成，正文进上下文等于模型写的内容反过来指导模型——沙盒对此无效（破坏发生在决策层）。
**代价**：技能能做的事变少；复杂技能需要"产出文件 + 请求宿主执行"两步。
**反悔成本**：中（放松容易，收紧难——所以一开始就收紧）。

---

## D7 · 记忆降为应用级 doc type

**决定**：内核只提供 `doc(type, scope, payload)`；`facts` 是其中一种 `DocKind`；双时态与冲突消解在应用层。
**理由**：家教需要"掌握度矩阵"、客服需要"客户档案+工单"；若 facts 是内核一等表，换场景必须改内核。
**代价**：内核失去对记忆语义的强约束。
**反悔成本**：低（加回约束比拆掉容易）。

---

## D8 · 三个数据平面分离

**决定**：状态（journal）/ 结论（docs）/ 资料（KB）分开存储与备份。
KB 的最小实现是**文件库**：内容按摘要落盘在 `files/`，索引是 `kind=file` 的 doc（名字/标签/大小/时间），
`keep` 存入、`files` 检索/取回/删除；`/ws` 仍是 7 天清理的草稿区。
**理由**：生命周期不同；KB 可整库重建，只需备份原始源；混在一起会导致备份成本与一致性都失控。
**代价**：三套保留策略要维护。
**反悔成本**：低。

---

## D9 · 四个扩展点：Channel / Store / Retriever / TurnDriver

**决定**：四个替换型 trait（Channel/Store/Retriever/TurnDriver），各配一致性测试；Store 用 Unit-of-Work；Retriever 在**接口上**独立于 Store，SQLite 实现**共享写线程**（FTS 是 Store 的投影）。
**理由**：换通道、换数据库、换检索是三种不同节奏的变化；把检索塞进 Store 会让每个后端重写一遍召回。
**代价**：多一层接口；需要 `EphemeralStore`/`EchoChannel` 两个桩来验证接口中立。
**反悔成本**：中（接口一旦被业务代码绕过就难收回，靠依赖守卫防止）。

---

## D10 · 沙盒：bwrap 白名单挂载 + cgroup v2

**决定**：`--unshare-all` + 显式白名单挂载（绝不 `ro-bind /`）+ cgroup `memory.max`/`pids.max` + `killpg` 超时。
挂载集固定为 `/usr` `/etc`（只读）、`/ws`（可写）、`/inbox` `/skills` `/media`（只读）、`/py` `/node`；
**唯一的扩展口**是 `[sandbox] mounts`（主人显式授权，见 D17），保留挂载点不可被覆盖。
**理由**：已在目标板实测（见 `PLATFORM.md`）：`/home` 不可见、外网不可达、600MB 分配被 `rc=137` 杀死；`RLIMIT_AS` 对 Python 不可靠。
**代价**：依赖 bwrap 存在；0.11 不支持部分新参数。
**反悔成本**：低（`ExecutionEnv` 可换实现，Landlock 已验证可用作后备）。

---

## D11 · 并发按 lane，不按数量

**决定**：`io=2`、`compile=1`（`nice 19`）、`external=1`；tokio `worker_threads=4`。
**理由**：整板约 0.3–0.6 个现代 x86 核，两个编译任务会把 timer 与长轮询饿到秒级抖动。
**代价**：并发利用率略低。
**反悔成本**：低（改配置）。

---

## D12 · 当前不做向量 / 多租户 / 插件热加载

**决定**：只做 FTS5；向量等知识库需求出现再上 `sqlite-vec`；不做多租户与动态库插件。
**理由**：数百条 facts 用 FTS5 足够；过早抽象无法正确设计。
**代价**：知识库场景暂时不支持。
**反悔成本**：低（`Retriever` 已预留；接口见 `INTERFACES.md`）。

---

## D13 · Telegram 用 HTML 而非 MarkdownV2

**决定**：`parse_mode=HTML`，自实现 markdown-lite → HTML 转换；流式期间同样走这条路径（转换器只在一对标记完整时才产出标签，未闭合围栏自动收尾，因此任意半截文本都是合法 HTML）。
**理由**：MarkdownV2 需要转义 ``_ * [ ] ( ) ~ ` > # + - = | { } . !`` 等十余个字符，漏一个就整条消息 400；HTML 只需转义 `& < >`，标签集合小且可枚举。
**代价**：能力上限低于 MarkdownV2（无 spoiler、无自定义 emoji），对我们无影响。
**反悔成本**：低（只影响渲染层）。

## D15 · 超级权限是「换执行环境」，不是「放宽沙盒」

**决定**：新增 `ExecProfile { Sandbox, Host, HostElevated }`，按 **run** 选择；默认 `Sandbox`。
- `Host`：以服务账号直接执行（查日志、看进程、装用户级软件），需 owner 显式指令，仅对下一条消息生效。
- `HostElevated`：通过 `/etc/sudoers.d/chuan` 的**命令白名单**提权，**逐条审批**；模型无法扩展白名单。
- 不可逆操作先 `--dry-run` 并展示 diff；变更前做 DB + 配置快照，失联 5 分钟看门狗回滚。

**理由**：把 `allow_host` 做成沙盒上的开关，等于把"隔离"和"授权"混成一件事，最终只能二选一（全隔离或全裸奔）。用 `ExecutionEnv` 的第二个实现承载，隔离边界不变，只是换了执行位置。

**代价**：需要维护 sudoers 白名单与快照/回滚；能力上限由白名单决定，不由模型决定。

**实现约束（强制）**：
- 宿主/提权子进程一律 `env -i` 启动，**不挂载 `$CREDENTIALS_DIRECTORY`**，不透传任何 `*_FILE`/`*_KEY` 环境变量；
- 某个工具确实需要凭据时，由内核以 fd（stdin）传入，用完即关，不落盘、不进日志；
- 拒绝实现"给 Host 继承环境"的捷径——那等于把密钥交给 agent。

**反悔成本**：低（profile 是参数；实现后置到 P5）。

## D16 · 身份：配置是种子，运行期靠 owner 批准

**决定**：`User ↔ Binding` 两层。`[identity]` 里的绑定是**引导**（唯一信任起点，只能改文件）；
运行期新增用户/绑定落库，且**必须由 owner 批准**（审批卡或一次性邀请码）。

**理由**：先有鸡还是先有蛋——第一个账号不可能自举，只能来自"能改这台机器配置的人"（文件权限即根信任）。
之后的账号如果允许自助注册，任何找到 bot 的人都能进来；如果只能改配置，家人加一次就要重启一次。
所以：种子走配置，扩容走审批。

**代价**：多一张表 + 一条审批路径；`default_user` 必须在出现第二个真人前删掉，否则越过审批。

**反悔成本**：低（绑定是数据，可删可迁）。

## D17 · 领域能力下沉为技能，内核只给通用口子

**决定**：内核不提供 `print` 这类领域工具。打印、发现、查墨量由技能实现；内核只提供
`[sandbox] mounts`（把 `/run/cups` 这类宿主服务只读/读写挂进沙盒）与联网 lane（`network: true`）。

**理由**：把 `lp` 封装成工具 = 绑定 CUPS。换一个没有 CUPS 的环境（裸 IPP、Windows 打印服务）就得改内核；
而技能可以改。框架的扩展性来自“agent 能自己写技能”，不是“内核内置更多工具”。
同一条原则也适用于 MCP：`tools/list` 是**协议能力**（进内核），某个服务的 API 语义是**领域知识**（进 playbook/技能）。

**代价**：`mounts` 是能力授权，挂 `/run/cups` 等于沙盒里任何代码都能提交/取消打印任务
（挂 `docker.sock` 就是容器逃逸级别）。所以只能由主人写进配置，模型只能建议。

**反悔成本**：低（挂载是配置；工具也没写）。

## D18 · 凭据只在宿主侧：不挂沙盒、不做通用出口代理

**背景**：上板后发现 `/etc` 是整块只读挂进沙盒的，而 `dida_token` / `weread_token` 是
`0440 root:chuan`——沙盒进程的 gid 也是 `chuan`，于是沙盒里的脚本能直接读走 token。
更一般地：daemon 与沙盒**同 uid**，在“路径可见”的前提下，`0400 chuan` / `0440 root:chuan`
都可读，`0400 root:root` 则 daemon 也读不了。**权限位无法把两者分开。**

**决定**：

1. **凭据的值永不进入沙盒**。`/etc` 里的凭据目录在两条 lane 都用空 tmpfs 遮掉
   （`BwrapEnv::with_masked_dir`）；沙盒里看到的是空目录。
2. **只支持“单次请求”级别的注入**，由宿主在发请求前解析：
   - 位置：header 模板、query 参数、JSON body 字段、path 占位符；
   - 模板变量：`{token}` `{secret}` `{sign}` `{ts_s}` `{ts_ms}` `{path}`；
   - 签名：HMAC-SHA256（钉钉 `{ts_ms}\n{secret}`、飞书 `{ts_s}\n{secret}`），
     可 base64 / base64url / hex；
   - 请求体可以来自 `/ws` 的文件（`body_file`）：**脚本负责算，宿主负责发**。
3. **不做通用出口代理**（原 P2 方案：unix socket + 明文 HTTP + 能力串）。理由见下。
4. **值不落地**：工具输出进上下文/账本前过一遍泄漏检测（`harness_kernel::leak`），
   响应与错误里出现的本次凭据值一律替换成 `***`；审计日志里的 path 也打码。

**为什么不做出出口代理**：它能让任意脚本透明携带凭据，但代价是——要覆盖 `https` 就得
MITM（自签 CA 进沙盒信任库）；要覆盖两条 lane 就得在离线 netns 里再起一个转发进程；
能力串、租约、限流、审计全都要自己维护。而实测（IronClaw 的使用经验）表明：只要沙盒里
**有任何**可供模型摆弄的凭据形态（哪怕只是占位符），模型就会尝试 base64、塞环境变量、
换协议头去绕过——**靠形状禁止是无限军备竞赛**。真正的边界只能是“值不在场”。

**参照**：IronClaw（`nearai/ironclaw`）用“占位符 `icsbx_` + 一次性租约 + 宿主出口注入 +
泄漏检测”解决同一问题；其中出口代理（`W6-EGRESS-PROXY`）在其文档里标注为**尚未实现**。
我们采用它的“值不在沙盒”与“出口清洗”两条，放弃多租户 AAD 加密与全量代理。

**非目标**：OAuth2 令牌交换（需要缓存 + 过期刷新）、AWS SigV4、OAuth1、mTLS 客户端证书。
出现真实需求时再单独设计，不预先抽象。

**代价**：

- 复杂脚本（多步签名、分片上传）不能直接带凭据——必须把“能算的部分”留在脚本、
  “要签名的部分”交给宿主；
- `path` 里注入凭据（飞书的 hook id）会进上游访问日志，只能保证**我们自己的**日志打码；
- 签名算法只支持 HMAC-SHA256。

**反悔成本**：中（若真要做代理，`auth`/`services` 这层可以保留，代理只是换一个调用方）。
