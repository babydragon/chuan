# 关键决策记录（ADR）

> 每条记录：**决定 · 理由 · 代价 · 反悔成本**。被推翻的决定保留在 §13，说明推翻了什么。
> 术语以 `GLOSSARY.md` 为准。

---

## D1 · 语言与部署形态：Rust 单二进制

**决定**：Rust 单二进制 + systemd，跑在目标板本地；不引入 Node/容器编排。
**理由**：目标机 riscv64；单二进制便于交叉编译与部署；无中间件运维。
**代价**：生态比 TS 弱，需要自己写不少编排代码。
**反悔成本**：高（等于重写）。
**备选**：Pi/Node 方案（曾设计为 v0.2，因运行时要求被否决，见 §13）。

---

## D2 · LLM 层自写，接口冻结为 `TurnDriver`

**决定**：自写 OpenAI 兼容客户端（约 400 行）+ 自己的 turn 状态机；不依赖 rig 的 `AgentRun`。
**理由**：① journal-first 决定了 loop 必须归我们；② rig 的 `AgentRun` 只能在轮边界重建、重建后计数器归零、修复产物（synthetic 消息）仍需自己入账；③ rig wire 层每两周一次破坏性变更（12 个月 22 个 minor、167 条 breaking）；④ 另两个候选各有硬伤（`async-openai` 丢 `reasoning_content`；`openai-api-rs` 流式 tool-call 丢分片）。
**代价**：约 400 行协议代码；方言差异要自己处理。
**反悔成本**：低——`TurnDriver` 是 trait，可把 rig wire 层作为第二实现接入。
**失败条件**：若自写客户端在三种 provider 上都无法稳定解析，再切 rig。

---

## D3 · Journal 是唯一真相

**决定**：持久化只信任 journal（消息、工具调用、任务、审批）；不持久化任何框架的内存状态。
**理由**：框架状态含 opaque reasoning、cache 标记、provider 元数据；升级或换 provider 即废。日志是 provider 无关、可审计、可重放的。
**代价**：需要自己实现恢复；journal 要含 `synthetic` 种类以保存模型插入的纠正性内容。
**反悔成本**：低（只是"多存一层"的反方向）。
**验收**：任一崩溃点恢复后，不产生重复的工具副作用；`synthetic(repair)` 事件不会因恢复而重复生成（历史中本就存在的非法调用除外）。

---

## D4 · 恢复按崩溃点分级 + 副作用三级

**决定**：不追求逐 token 续写；按"用户消息/流式中/工具未执行/工具执行中/终稿未送达"分别处理；副作用分 `Pure`/`Idempotent(key)`/`External`。
**理由**：重放整个 turn 会重复副作用；家庭场景重发一条消息的代价远低于重复打印。
**代价**：交互 turn 是 at-most-once，极端情况下用户可能看到"重发"提示。
**反悔成本**：低（可在 `External` 上放宽为"至少一次 + 去重按钮"，已实现）。

---

## D5 · 授权轴是能力越界，不是命令黑名单

**决定**：按**执行域**审批（共 8 个，见 `harness-kernel/src/policy.rs`）——`sandbox`（免审批）/ `self_modify`（问）/ `outbound`（域名白名单即授权）/ `lan`（问）/ `install`（问）/ `host`（问，L1）/ `host_elevated`（默认拒绝，L2）/ `host_observe`（默认放行，L3），见 `[policy]`。黑名单只作快速失败提示，不作为安全边界。
**理由**：沙盒已是边界（`/usr` 只读、`/home` 不可见、无网、cgroup 硬限），命令名不决定后果；按命令审批会训练橡皮图章。工具只是入口，真正要判的是"有没有出沙盒"。
**代价**：依赖沙盒可用性；沙盒降级时必须自动收紧为命令白名单 + 全审批。出网的闸从"逐次确认"挪到"域名白名单"，白名单过宽等于放开外泄通道。
内网调试（`lan`）是例外：bwrap 只能整块隔离或放开网络，无法"只通内网"，因此该 lane 保留网卡但**看不到任何宿主文件与凭据**，
并逐条审批；网上导入的技能跑在离线的 `exec` 里，结构上够不到它。
**反悔成本**：低（策略是配置）。

---

## D6 · 技能是纯函数，且权限不可自授

**决定**：技能只读写 workspace；`SKILL.md` 正文永不进上下文（只注入结构化 manifest）；`network` 等权限由策略层授予，不由技能声明。
**理由**：`SKILL.md` 由模型自己生成，正文进上下文等于模型写的内容反过来指导模型——沙盒对此无效（破坏发生在决策层）。
**代价**：技能能做的事变少；复杂技能需要"产出文件 + 请求宿主执行"两步。
**反悔成本**：中（放松容易，收紧难——所以一开始就收紧）。

---

## D7 · 记忆降为应用级 doc type

**决定**：内核只提供 `doc(type, scope, payload)`；`facts` 是其中一种 `DocKind`；双时态与冲突消解在应用层。
**理由**：家教需要"掌握度矩阵"、客服需要"客户档案+工单"；若 facts 是内核一等表，换场景必须改内核。
**代价**：内核失去对记忆语义的强约束。
**反悔成本**：低（加回约束比拆掉容易）。

---

## D8 · 三个数据平面分离

**决定**：状态（journal）/ 结论（docs）/ 资料（KB）分开存储与备份。
KB 的最小实现是**文件库**：内容按摘要落盘在 `files/`，索引是 `kind=file` 的 doc（名字/标签/大小/时间），
`keep` 存入、`files` 检索/取回/删除；`/ws` 仍是 7 天清理的草稿区。
**理由**：生命周期不同；KB 可整库重建，只需备份原始源；混在一起会导致备份成本与一致性都失控。
**代价**：三套保留策略要维护。
**反悔成本**：低。

---

## D9 · 四个扩展点：Channel / Store / Retriever / TurnDriver

**决定**：四个替换型 trait（Channel/Store/Retriever/TurnDriver），各配一致性测试；Store 用 Unit-of-Work；Retriever 在**接口上**独立于 Store，SQLite 实现**共享写线程**（FTS 是 Store 的投影）。
**理由**：换通道、换数据库、换检索是三种不同节奏的变化；把检索塞进 Store 会让每个后端重写一遍召回。
**代价**：多一层接口；需要 `EphemeralStore`/`EchoChannel` 两个桩来验证接口中立。
**反悔成本**：中（接口一旦被业务代码绕过就难收回，靠依赖守卫防止）。

---

## D10 · 沙盒：bwrap 白名单挂载 + cgroup v2

**决定**：`--unshare-all` + 显式白名单挂载（绝不 `ro-bind /`）+ cgroup `memory.max`/`pids.max` + `killpg` 超时。
挂载集固定为 `/usr` `/etc`（只读）、`/ws`（可写）、`/inbox` `/skills` `/media`（只读）、`/py` `/node`；
**唯一的扩展口**是 `[sandbox] mounts`（主人显式授权，见 D17），保留挂载点不可被覆盖。
**理由**：已在目标板实测（见 `PLATFORM.md`）：`/home` 不可见、外网不可达、600MB 分配被 `rc=137` 杀死；`RLIMIT_AS` 对 Python 不可靠。
**代价**：依赖 bwrap 存在；0.11 不支持部分新参数。
**反悔成本**：低（`ExecutionEnv` 可换实现，Landlock 已验证可用作后备）。

**实现状态（2026-10-28 核对）**：bwrap 白名单挂载与 `killpg` 已实现；**`memory.max` / `pids.max`
的 per-exec 限额尚未实现**——当前内存边界只有 systemd 服务级 `MemoryMax=1G` 兜底，
加上沙盒 `/tmp` 的 256MB 上限。`PLATFORM.md` 里"600MB 分配被 `rc=137` 杀死"是
`systemd-run --scope -p MemoryMax=` 的实测，验证的是 **cgroup 机制可用**，不是单次 `exec` 已受限。
缺口登记在 `SBC-VERIFY.md` 末尾；实现方式待定（per-exec scope 需要 user manager，或直接写 cgroup v2）。

## D11 · 并发按 lane，不按数量

**决定**：`io=2`、`compile=1`（`nice 19`）、`external=1`；tokio `worker_threads=4`。
**理由**：整板约 0.3–0.6 个现代 x86 核，两个编译任务会把 timer 与长轮询饿到秒级抖动。
**代价**：并发利用率略低。
**反悔成本**：低（改配置）。

---

## D12 · 当前不做向量 / 多租户 / 插件热加载

**决定**：只做 FTS5；向量等知识库需求出现再上 `sqlite-vec`；不做多租户与动态库插件。
**理由**：数百条 facts 用 FTS5 足够；过早抽象无法正确设计。
**代价**：知识库场景暂时不支持。
**反悔成本**：低（`Retriever` 已预留；接口见 `INTERFACES.md`）。

---

## D13 · Telegram 用 HTML 而非 MarkdownV2

**决定**：`parse_mode=HTML`，自实现 markdown-lite → HTML 转换；流式期间同样走这条路径（转换器只在一对标记完整时才产出标签，未闭合围栏自动收尾，因此任意半截文本都是合法 HTML）。
**理由**：MarkdownV2 需要转义 ``_ * [ ] ( ) ~ ` > # + - = | { } . !`` 等十余个字符，漏一个就整条消息 400；HTML 只需转义 `& < >`，标签集合小且可枚举。
**代价**：能力上限低于 MarkdownV2（无 spoiler、无自定义 emoji），对我们无影响。
**反悔成本**：低（只影响渲染层）。

## D15 · 超级权限是「换执行环境」，不是「放宽沙盒」

> **已被 D22 取代（授权表 + 独立 root 单元）**。本节保留为历史：`ExecProfile` 三分法与
> `/etc/sudoers.d/chuan` 命令白名单在当前代码里**都不存在**，现行形态见 D22。

**决定**：新增 `ExecProfile { Sandbox, Host, HostElevated }`，按 **run** 选择；默认 `Sandbox`。
- `Host`：以服务账号直接执行（查日志、看进程、装用户级软件），需 owner 显式指令，仅对下一条消息生效。
- `HostElevated`：通过 `/etc/sudoers.d/chuan` 的**命令白名单**提权，**逐条审批**；模型无法扩展白名单。
- 不可逆操作先 `--dry-run` 并展示 diff；变更前做 DB + 配置快照，失联 5 分钟看门狗回滚。

**理由**：把 `allow_host` 做成沙盒上的开关，等于把"隔离"和"授权"混成一件事，最终只能二选一（全隔离或全裸奔）。用 `ExecutionEnv` 的第二个实现承载，隔离边界不变，只是换了执行位置。

**代价**：需要维护 sudoers 白名单与快照/回滚；能力上限由白名单决定，不由模型决定。

**实现约束（强制）**：
- 宿主/提权子进程一律 `env -i` 启动，**不挂载 `$CREDENTIALS_DIRECTORY`**，不透传任何 `*_FILE`/`*_KEY` 环境变量；
- 某个工具确实需要凭据时，由内核以 fd（stdin）传入，用完即关，不落盘、不进日志；
- 拒绝实现"给 Host 继承环境"的捷径——那等于把密钥交给 agent。

**反悔成本**：低（profile 是参数）。

**实现形态（2026-10-29 修订，见 D22）**：`HostElevated` **不走 sudoers**。`deploy/chuan.service`
是 `NoNewPrivileges=yes`，服务里 `sudo` 根本起不来；拆掉它等于为了一个能力放弃整条加固链。
改为**同二进制第二单元** `chuan hostd`（`User=root`）+ unix socket + `SO_PEERCRED`，
白名单从 `/etc/sudoers.d/chuan` 挪到 hostd 的授权表（数据文件）。

## D16 · 身份：配置是种子，运行期靠 owner 批准

**决定**：`User ↔ Binding` 两层。`[identity]` 里的绑定是**引导**（唯一信任起点，只能改文件）；
运行期新增用户/绑定落库，且**必须由 owner 批准**（审批卡或一次性邀请码）。

**理由**：先有鸡还是先有蛋——第一个账号不可能自举，只能来自"能改这台机器配置的人"（文件权限即根信任）。
之后的账号如果允许自助注册，任何找到 bot 的人都能进来；如果只能改配置，家人加一次就要重启一次。
所以：种子走配置，扩容走审批。

**代价**：多一张表 + 一条审批路径；`default_user` 必须在出现第二个真人前删掉，否则越过审批。

**反悔成本**：低（绑定是数据，可删可迁）。

**实现状态（2026-10-30）**：运行期绑定与审批路径**未实现**，本期只做"配置写死"
（见 D26）。D16 的审批/邀请码保留为未来扩展，不删。

## D17 · 领域能力下沉为技能，内核只给通用口子

**决定**：内核不提供 `print` 这类领域工具。打印、发现、查墨量由技能实现；内核只提供
`[sandbox] mounts`（把 `/run/cups` 这类宿主服务只读/读写挂进沙盒）与联网 lane（`network: true`）。

**理由**：把 `lp` 封装成工具 = 绑定 CUPS。换一个没有 CUPS 的环境（裸 IPP、Windows 打印服务）就得改内核；
而技能可以改。框架的扩展性来自“agent 能自己写技能”，不是“内核内置更多工具”。
同一条原则也适用于 MCP：`tools/list` 是**协议能力**（进内核），某个服务的 API 语义是**领域知识**（进 playbook/技能）。

**代价**：`mounts` 是能力授权，挂 `/run/cups` 等于沙盒里任何代码都能提交/取消打印任务
（挂 `docker.sock` 就是容器逃逸级别）。所以只能由主人写进配置，模型只能建议。

**反悔成本**：低（挂载是配置；工具也没写）。

## D18 · 凭据只在宿主侧：不挂沙盒、不做通用出口代理

**背景**：上板后发现 `/etc` 是整块只读挂进沙盒的，而 `dida_token` / `weread_token` 是
`0440 root:chuan`——沙盒进程的 gid 也是 `chuan`，于是沙盒里的脚本能直接读走 token。
更一般地：daemon 与沙盒**同 uid**，在“路径可见”的前提下，`0400 chuan` / `0440 root:chuan`
都可读，`0400 root:root` 则 daemon 也读不了。**权限位无法把两者分开。**

**决定**：

1. **凭据的值永不进入沙盒**。`/etc` 里的凭据目录在两条 lane 都用空 tmpfs 遮掉
   （`BwrapEnv::with_masked_dir`）；沙盒里看到的是空目录。
2. **只支持“单次请求”级别的注入**，由宿主在发请求前解析：
   - 位置：header 模板、query 参数、JSON body 字段、path 占位符；
   - 模板变量：`{token}` `{secret}` `{sign}` `{ts_s}` `{ts_ms}` `{path}`；
   - 签名：HMAC-SHA256（钉钉 `{ts_ms}\n{secret}`、飞书 `{ts_s}\n{secret}`），
     可 base64 / base64url / hex；
   - 请求体可以来自 `/ws` 的文件（`body_file`）：**脚本负责算，宿主负责发**。
3. **不做通用出口代理**（原 P2 方案：unix socket + 明文 HTTP + 能力串）。理由见下。
4. **值不落地**：工具输出进上下文/账本前过一遍泄漏检测（`harness_kernel::leak`），
   响应与错误里出现的本次凭据值一律替换成 `***`；审计日志里的 path 也打码。

**为什么不做出出口代理**：它能让任意脚本透明携带凭据，但代价是——要覆盖 `https` 就得
MITM（自签 CA 进沙盒信任库）；要覆盖两条 lane 就得在离线 netns 里再起一个转发进程；
能力串、租约、限流、审计全都要自己维护。而实测（IronClaw 的使用经验）表明：只要沙盒里
**有任何**可供模型摆弄的凭据形态（哪怕只是占位符），模型就会尝试 base64、塞环境变量、
换协议头去绕过——**靠形状禁止是无限军备竞赛**。真正的边界只能是“值不在场”。

**参照**：IronClaw（`nearai/ironclaw`）用“占位符 `icsbx_` + 一次性租约 + 宿主出口注入 +
泄漏检测”解决同一问题；其中出口代理（`W6-EGRESS-PROXY`）在其文档里标注为**尚未实现**。
我们采用它的“值不在沙盒”与“出口清洗”两条，放弃多租户 AAD 加密与全量代理。

**非目标**：OAuth2 令牌交换（需要缓存 + 过期刷新）、AWS SigV4、OAuth1、mTLS 客户端证书。
出现真实需求时再单独设计，不预先抽象。

**代价**：

- 复杂脚本（多步签名、分片上传）不能直接带凭据——必须把“能算的部分”留在脚本、
  “要签名的部分”交给宿主；
- `path` 里注入凭据（飞书的 hook id）会进上游访问日志，只能保证**我们自己的**日志打码；
- 签名算法只支持 HMAC-SHA256。

**反悔成本**：中（若真要做代理，`auth`/`services` 这层可以保留，代理只是换一个调用方）。

## D19 · 子 agent：单层派生、结论回传、工具裁剪

**决定**：

1. 形态只有两种：**前台委托**（父 turn 内阻塞工具，≤120s，随父取消）与**后台 Task**
   （durable doc 行 + 5s tick 领取，见 `ROADMAP.md` P4.3）。不做第三种。
2. **拓扑单层**：`depth ≤ 1`。子 agent 的工具集**不含** `delegate`——用工具集禁止，不靠提示词。
3. 子 agent 有**独立 Conversation**（`sub:<parent_conv>#<n>`）与独立 run/journal，**不共享父历史**。
   回传 `Conclusion{status, summary ≤2000 字, child_conv, artifacts[], pending_actions[], usage}`；
   超长结论按字符截断并指向子会话——**完整过程在账本里，不另存一份文件**。
   父上下文净增一条 `msg.tool_result`。
4. **子 agent 不得请求审批**：只装配免审批域工具（`read` / `write` / `exec` / `playbook` /
   `web_fetch` / `keep` / `files`）；命中 `ask` 域直接失败，不挂起等人。
5. 子 agent 与父**共用 system prompt 字节与工具数组前缀**：`Tool::tier()`（0 通用 / 1 父级专用）
   排序后只削尾部，以命中 provider 的 prompt cache。
6. **需要审批的动作交回父会话**：结论带 `pending_actions`（子 agent 按 `[待父执行]` 分节写），
   父在本轮决定做不做。子 agent 不弹卡、不挂起——它没有通道，弹卡等于绕过治理。
7. **角色是配置，不是模型自由发挥**：`[agents.roles.<name>]` 给一份提示词 + 模型 + 工具子集 + 预算；
   `delegate(role="coder")` 只能点名。工具三层收窄（`[agents] tools` → 角色 → profile），
   提示词**追加在父前缀之后**（前缀字节不变，cache 仍命中），拼错角色名直接报错、不静默回退。
8. **接手只给简报，不重放历史**：`delegate(continue_from=…)` / `/tasks retry` 时，
   内核从上一个任务或子会话里提取**结论与产物路径**（≤1600 字）注入新子 agent，
   不复制历史消息。子会话 id 只能在本父会话名下使用（防止跨会话串数据）。
   理由：续跑的价值是"别从零开始"，不是"假装还是同一个进程"；把整段历史搬过去
   既费 token，又会让新子 agent 误以为那些步骤是它自己做的。
9. **父 agent 能管自己派的任务**：`task(action=list|status|cancel)`（`tier=1`、`Sandbox` 域）。
   理由：`delegate(background=true)` 之后父只能干等，用户问"怎么样了"它只能编。给它查询与取消权，
   但**不鼓励轮询**（完成会推消息）。**前台委托管不了**：模型在被阻塞时无法调用任何工具，
   只能靠 `/cancel` 或角色的 `wall_ms`——这是阻塞式委托的固有代价。
10. **角色可由 agent 注册，但要人批**：`role(action=add|list|remove)` 写 `roles_dir/<name>.{toml,md}`，
   域 `SelfModify`（逐次审批）、`tier=1`（子 agent 拿不到）。注册完**热加载**，下一次 delegate 即可用；
   父会话的 system 里会多一段"可派角色"清单，模型据此知道有几个"小弟"、各能做什么。

**理由**：父上下文是稀缺资源（实测每请求 prompt 中位 3.7k、p80 6.5k token），子 agent 的价值是
"过程不进父历史"，不是并行度；SBC 上真正的瓶颈是 CPU 与模型连接，不是线程数。
审批必须由人确认，而子 agent 没有通道，**能委托审批就等于绕过治理**（D5）。

**代价**：

- 委托常态下**更贵**：子 agent 要重付一次前缀，token 约 +10~30%；只有"读大材料"或"父历史接近
  `context_budget_tokens`"时才省。**不能拿"省 token"当采用理由。**
- 前台委托期间父无输出，延迟 +8~20s；必须显示状态行。
- 子 agent 不能沉淀技能/装依赖，复杂任务仍要回父层完成。

**反悔成本**：低（拓扑是配置与工具集；真要做网状协作是另一次设计，不是放松本条）。

**已评估但暂不做**：把父已获批的域作为一次性能力传给子（预授权）。触发条件与约束见
`ROADMAP.md` §5「已评估但未实现：预授权能力」。

**验收**：子 run 结束后父上下文只增一条 `msg.tool_result`；子工具集里没有 `delegate`；
子 agent 调 `http` 立即失败而不是挂起等审批。

## D20 · 成本归属与闸门：按 token 记账、按服务商窗口兜底（金额估算不实现）

**决定**：

1. `usage.recorded` 增加 `agent` 与 `parent_run`；`usage_rollup` 增 `run_id` / `agent` 两列（schema V5）。
   子 agent 的 token 同时计入父 run 汇总与全局日/月额度。
2. 每次 spawn 前过**闸门**：`depth`、单 run 子数（默认 2）、`agent` lane 并发（默认 1）、
   日 token 上限、月 token 上限。任一不过直接拒绝，不排队。
3. 单 child 预算：`max_turns=6`、`max_tokens=20k`、`wall_ms=120000`；超限返回
   `Conclusion{status=budget}`，不崩、不自动重试。
4. **金额估算不实现**：没有 `[pricing]` 段，`cost_est` 恒为 `0.0`（`harness-kernel/src/budget.rs`
   与 `engine` 都写死），`/usage` 遇到 0 明说"金额未配"，不假装免费。
   钱的兜底交给**服务商自己的窗口**：402/429 归为 `EngineError::Quota{message, retry_after_s}`，
   直接停 run、不自动重试，并把"额度已用尽 + 约多久可再试"回给主人（5 小时 / 每周 / 每月口径由服务商给）。
5. 观测：`/usage`（今日/本月，按 agent 与 conv 分）、`/agents`（运行中子 agent，可取消）、
   `/tasks`（后台任务进度）。
6. **缓存命中单独记账**（schema V7）：`usage_rollup` / `usage.recorded` 增 `cache_hit_tokens` 与
   `cache_write_tokens`，只存原始 token，命中率查询时算；`/usage` 按模型分行展示，跨模型不平均。
   解析层把 DeepSeek（`prompt_cache_hit_tokens`）、OpenAI/智谱（`prompt_tokens_details.cached_tokens`）、
   Anthropic（`cache_read/creation_input_tokens`）归一化为"输入包含命中"的统一口径。
   目的：换模型（如 DeepSeek 缓存命中/未命中差价大）前先有基线，后续据此优化上下文前缀稳定性。
   仍旧不引入 `[pricing]`：缓存 token 数本地能算准，单价随时变。

**理由**：没有账本的多 agent 是费用放大器。实测基线：37 个有用量的 run 均 9.4k prompt token，
一次委托 ≈ 一次普通 run——放大倍数就等于派发次数，必须有硬闸门。
闸门建在 **token** 上而不是金额上：token 是本地能算准的数，价目随时变、还要按模型维护一张表；
真正的"钱包见底"由服务商先告诉我们（Quota 错误），补一张价格表既不及时也不省钱。

**代价**：多一层账本与配置；子 agent 失败会以"预算耗尽"而非"崩溃"呈现，必须靠 `/agents` 才能看清。

**反悔成本**：低（预算都是配置；账本是 append-only 事件，可加不可改）。

## D21 · system 指令三段式：核心写死，配置只能追加

**决定**：`system = 核心段（编译进二进制）→ system_prompt_append_file`。只有一个追加口，
不能整体替换核心。`/prompt` 打印最终生效的全文（按 3000 字分条）。

**迁移**：`system_prompt_extra_file` 保留为别名（启动时提示改名）；`system_prompt_file` 直接报错——
它过去是"整体替换"，语义改成追加后若继续静默接受，人们会以为核心已被覆盖。

**理由**：可替换的 system 一旦被改过几次，"默认规则是什么"就没人说得清——安全边界（沙盒、审批、
不声称厂商身份、准确性优先）会被无意抹掉，而且无法排查"为什么它今天这么说话"。
写死的核心 + 可追加大段，让"改得动"和"说得清"同时成立。

**代价**：
- 想彻底换掉人设/规则的人做不到（只能追加一段，冲突时以追加段为准，但核心仍在上下文里）。
- 核心段变长会挤占每轮预算（当前约 1.6k 字），改动要克制。

**反悔成本**：低（把 `system_prompt_file` 重新当覆盖用是一行判断；但会回到"说不清默认"的老问题）。

## D22 · 宿主执行：两条通用边界 + 数据化授权

**决定**：让 agent 能管理所在机器，但**不新增任何领域工具**。新增两个执行边界 + 一个只读面，
其余全部是数据：

1. **`Host`（L1）**：bwrap + 路径白名单 + 宿主 netns，以服务账号身份执行。
   **不** `--unshare-pid`，且 `--ro-bind /proc /proc`（要的是宿主进程视图，不是新 procfs）。
2. **`HostElevated`（L2）**：同二进制第二单元 `chuan hostd`（`User=root`），unix socket +
   `SO_PEERCRED` 校验对端 uid；只做「argv 前缀匹配 → `env -i` 执行 → 写审计」，
   **不含** `pkg.install` / `unit.start` 这类动词（连"包管理器是谁"都不该由它判断——
   客户端只发 argv，语义由授权表与 playbook 承载）。
3. **`sys`（L3）**：只读观测。`/proc`、`/sys` 进程内直接读；`journalctl` / `systemctl show`
   这类固定命令由内核**自己**以 `env -i` 直连执行，不经 bwrap。理由不是"bwrap 连不上总线"
   （那是漏挂 `/run/systemd/system` 的误判，已修正），而是：**固定读接口不需要通用 lane**——
   为一行的指标去开放整个宿主文件系统与 netns 是过度授权。argv 恒定，没有注入面。

授权是**数据**：`[host.path]`（路径 → `ro`/`rw` + `approval`）、`[[host_elevated.grant]]`
（argv 前缀 → `approval` + `snapshot`）。授权表**按 mtime 热加载**——加一条不用重启，
因为重启会打断 agent 正在跑的那一轮，而"开口子"恰恰发生在这时。解析失败 fail-closed。
（第三份数据是**命令条目表** `commands.d/`，见 D31：它不由人手写，而是内核在主人批准后写，
而且条目是**封闭参数**而非开尾 argv 前缀。）

权限三档 scope：

| scope | 落点 | 权限 | 备注 |
|---|---|---|---|
| 本次调用（临时挂载） | 调用参数 `grant[]` | **只能 ro** | ≤ 8 条、点名才挂、不落盘 |
| 本对话 | 审批卡勾选 | ro | 1800s 上限，重启即失效 |
| 持久 | 授权表 `[host.path]`，**人手写** | ro / rw | `always`（默认挂载、免问）/ `once`（默认不挂、每次点名，只读） |

`approval` 落在路径条目上，语义是**"在不在默认挂载集里"**——这条 lane 的命令是任意的，
无法从 argv 反推"这次碰了哪个目录"，所以只能在挂载集上区分。`rw` 必须配 `always`
（写错的代价不可逆，而"临时可写"是最容易失守的那一格）。

拒绝必须**结构化**（`NotGranted { kind, item, hint }`）——"缺什么"要能机器读出，
否则申请单只能靠模型猜，人没法审。

扩展闭环：结构化拒绝 → `capability(request)` **只写草稿并通知**（不自动改配置）→ 人改文件 →
下一轮生效。申请单固定 8 节（现场/最小请求/必要性/可见范围/更小选项/副作用/回滚/自验），
SOP 五条硬规则随二进制发布，可按项目惯例用 `~/.config/chuan/playbooks/capability.md` 覆盖。

**理由**：取舍落在"什么该固化"。**边界**（在哪跑、看得见什么、凭据在哪）与**治理**
（审批、审计、快照、恢复）固化；**领域语义**（装哪个包、管哪个 unit、怎么做）下沉为数据与技能
（D17）。判据是不变量 15 那句"换一个环境还要改 Rust 吗"：apt 换 dnf 不该改，SSH 到另一台机器该改。
于是 Rust 的开口数从"每场景一次"降为"每类边界一次"（共 3 个：`Host` 环境、`hostd`、
`capability` 工具）。

**代价**：
- 授权表比动词表弱：`["/usr/bin/apt-get","install"]` 一条等于放行它全部后续参数，
  而 maintainer scripts 本身就是 root 执行。只能靠逐次审批 + `apt-get -s` 预览 + dpkg 快照兜底。
- L1 的可见范围是一份清单，漏一条的表现是"命令莫名失败"，比权限错误难查。
- 多一个 root 单元要维护（`chuan hostd`）：日志、重启、装脚本都要多一道。

**实现约束（强制）**：
- 强制遮蔽、**调用级不可覆盖**：`/etc/chuan/secrets`、`/etc/chuan/services.d`、`/etc/chuan/chuan.toml`；
  保留 `roles/` 与 `playbooks/`（agent 自己要读）。理由：`services.d/*.toml` 里写着 `token_file` 路径，
  `chuan.toml` 里有完整策略，把它们交给一次"临时挂载"没有意义。
- L1/L2 一律 `env -i`，不挂 `$CREDENTIALS_DIRECTORY`，不透传 `*_FILE` / `*_KEY`（同 D15）。
- **临时挂载（`grant[]`）只允许 ro**；rw 必须落成表内一行。写错的代价不可逆，而"临时批准可写"
  正是橡皮图章最容易失守的地方。
- **资产绑定审批**：免问的判据是 `(授权表条目, 展开后的 argv 前缀 / 规范化路径)`，
  不是工具名——否则一条 `always` 等于放行整类命令。
- 逐次审计：`host-access.jsonl`（第几条授权、展开后的 argv、退出码、耗时），与 `net-access.jsonl` 并列。
- **可写路径由 unit 决定**：bwrap 的 `--bind` 不清除源挂载继承的 `MS_RDONLY`
  （2026-10-29 实测：ro 父挂载里 bind 出来仍不可写）。所以 L1 里"挂成 rw 却写不进"是正常现象，
  可写目录必须写进 unit 的 `ReadWritePaths`，且**只能写实际 uid 的路径**：
  system 单元里 `%U` 恒为 0，写 `/run/user/%U` 会变成 `/run/user/0` 并让服务起不来（实测 226/NAMESPACE）。
  `/run/user/<uid>` 本身只需 `ro`——`systemctl --user` 只连 socket。
- **自毁防护**：`chuan.service` 的 `restart` 排队到本轮 turn 结束后执行（先发消息再重启）；
  `stop` / `disable` 一律拒绝，要主人手工。
- 单位名称/路径不靠 argv 猜：hostd 匹配授权后再过一遍通用校验（拒绝 `..`、拒绝符号链接逃逸、
  拒绝命中强制遮蔽的祖先目录）。

**v1 明确不做**：
- **技能不能进宿主**：`run_skill` 仍只跑沙盒（联网 lane 由内核给，`network` 不由技能自授，D6）。
  宿主能力只经主会话的 `host` 工具，子 agent 也拿不到（`tier=1`）。
- agent 写系统级 unit 文件（`/etc/systemd/system/*`）：这类文件一年写不了几个，**人写一次**，
  agent 之后用 `systemctl` 管生命周期；否则模板校验又要把领域知识塞回 Rust。
- 其他账号目录的组 / ACL 方案（挂载给不了权限位，`0640` 照样读不到）。
- 公共 `/tmp` 式共享空间（以后按需再划）。
- per-exec cgroup（属 P4.3，见 `SBC-VERIFY §10`）。

**反悔成本**：低——两条边界都是 `ExecutionEnv` 实现，删掉不影响内核；授权表格式只影响配置解析。
真正难退的是"人写授权表"这个习惯：一旦退化成 agent 自批，整套设计就没有意义了。

## D23 · 通知类流程：SOP 是 playbook；写入需审批，但不能当权限用

**背景**：家人把老师/学校的通知原文粘进来，期望的是"解析时间与要点 → 定提醒点 → 润色 →
建提醒 → 存档 → 按渠道推送"。这类流程每两周就会变一次措辞与偏好。

**决定**：

1. **形态是 `playbook`，不是技能。** 解析与措辞需要判断，脚本化只会更脆；而且 `SKILL.md`
   正文永不进上下文（D6），承载不了"怎么想"。技能留给"确定性动作"。
2. **渠道不改内核**：
   - TG：`remind(message=…)`，到点原样发，零模型成本；
   - 钉钉：`remind(text=…)`，到点**重跑一轮**，由模型调 `http(service=dingtalk)` 发出。
   - 接受这一次 LLM 调用：延迟 ≈ 30s（提醒 tick）+ 数秒（首字）；
     用户口径是"1 分钟内可接受，**不遗漏优先于准时**"。
   - 零成本路由（`remind.notify = "service:xxx"`）**暂不做**；触发条件见下。
3. **存档**用 `remember(subject="学校通知", predicate="<YYYY-MM-DD> <事项>",
   value="要点｜时间=<绝对时间>｜渠道=<tg|dingtalk>｜remind=<id>")`；长原文用 `keep` 进文件库。
   `predicate` 用"日期 + 事项"当键，重复粘贴同一条通知天然幂等。
4. **允许 agent 写 playbook，但必须审批落盘**（`publish_playbook`）：
   审批卡显示变更行；`builtin` 主题（`capability` / `timer` / `distill` / `import-skill` /
   `schedule-job` / `webhook`）不可覆盖（要 `override=true` 且红字）；文件头强制三行溯源；
   正文 ≤20k；覆盖留 `.bak`。
5. **硬边界：playbook 不是权限依据。** 授权只认 `[policy]`、授权表与审批卡；代码从不读 playbook，
   所以"写一句可以跳过审批"没有任何效力。这条是结构事实，不是口头约定。

**理由**：
- 技能已经允许 agent 自沉淀（`publish_skill` = SelfModify + 审批 + 备份 + 回滚），SOP 是同一类东西；
- **记忆比 playbook 更危险**：`remember` 无需审批，且按检索自动注入上下文；playbook 必须模型主动取用。
  放开记忆却禁止写 playbook，是自相矛盾的防线；
- 判时规则写死在 SOP 里，避免每次"提前多久"都不一样。

**代价**：
- 多了一条"模型写的持久指令"通道（靠审批 + 溯源 + builtin 保护压住）；
- 审批卡上的 diff 有人不看就点（与所有审批项同性质）；
- **提醒有 2 小时补跑窗口**（`REMINDER_GRACE_MS`）：关机超过 2 小时这一次就丢——
  与"不遗漏"冲突。要么把窗口做成可配（24h），要么接受并记录在案。

**分两步走**：先由主人手写 SOP 跑两周（流程定型），再实现 `publish_playbook` 下放。
在未定型的流程上让 agent 反复改，只会把不确定性叠两层。
（**2026-11 提前实现**：KB 需要 agent 自己维护「这类资料怎么抽结构」的规范，见 D34；
`publish_playbook` 已按本文的形态落地：SelfModify + 审批 + 覆盖留 `.bak` + builtin 需 `override`。）

**反悔成本**：低——工具可删、`playbooks` 目录可以收回到 `0750`、builtin 保护本来就在。

**触发条件（满足任一才做）**：
- `publish_playbook`：SOP 两周内被手改 ≥3 次，或主人明确要求；
- `remind.notify`：每天 ≥3 条钉钉提醒，或到点那轮模型调用经常失败；
- 补跑窗口延长：出现一次"因为关机/重启漏发"，或主人明确要求。

## D24 · 消息状态回执：挂在入站消息上的原生表情，不额外发消息

**背景**：会话内是**串行**的——`handle_run` 按 `conversation` 拿互斥锁，后到的消息在内存里排队。
界面上只看到上一条回复在不停更新，于是"哪些已经收到、哪些还没开始处理"完全看不出来；
一次发三条时会以为前两条没被收到。

**决定**：

1. 状态回执挂在**入站消息本身**，用通道原生的 reaction（表情），**不新增消息**。
2. 四态：未开始 `😐` / 处理中 `👀` / 完成 `👍` / 失败 `👎`。
   **取消 = 清空**（既不是成功也不是失败）；**预算超限按失败**（用户视角确实没办成）。
3. `Channel::react(conversation, msg, emoji)` 是**带默认空实现**的 trait 方法。
   它不进 `View`、不归 Renderer：状态属于"这条入站消息"，不属于任何一次渲染快照。
4. **best-effort**：失败只记 trace，不影响 run 成败，也不阻塞 turn。
5. `Inbound` 增加 `msg: Option<MsgRef>`——平台侧消息句柄。合成消息（定时任务、polish、
   内部派发）为 `None`，此时 `react` 必然 no-op。
6. 状态点只有三个：**收到**（不管内容，先判该会话是否已有在跑的 run）、**拿到锁**、**收尾**。
   判"是否排队"用 `run()` 里按会话维护的**在途计数器**，不看 `runs`——`runs` 要等拿到锁才写入，
   同一批到达的消息会全部漏判（实测：三个 update 同批进来，`runs` 里一个都没有）。

**为什么是 reaction 而不是再发一条消息**：

- 一条消息就是一个气泡，N 条排队消息会刷屏，与"少打扰"冲突；
- Telegram 每个 bot 对每条消息**只能有一个 reaction**，每次调用是**替换**——天然就是个状态机；
- 表情挂在原消息下，天然把"状态"和"那条消息"绑在一起，不需要额外约定。

**emoji 是白名单**：Telegram 的 `ReactionTypeEmoji` 只接受固定 73 个 emoji，
`⏳`/`✅`/`❌` **都不在其中**（实测 `⏳` → `400 REACTION_INVALID`）。
选 `😐→👀→👍/👎` 是因为四个都在白名单内、语义直白。

**代价**：

- 三个状态 = 每条消息最多 3 次 API 调用；排队多时调用量线性上升（量级仍很小）。
- **微信（iLink）没有 reaction 接口**，同样信息只能靠发消息，而 iLink 每条入站只给
  10 条出站额度——所以**微信侧明确不做状态回执**，不是遗漏。
- 表情语义弱于文字；`😐` 与 `👀` 在部分主题下对比度不高。
- **重启后内存队列消失**，已挂 `😐` 的消息不会有人来改它——reaction 会停在旧状态。
  这是进程内队列的固有限制，不为此引入持久队列。

**反悔成本**：低。trait 方法有默认实现，删掉只影响 Telegram 一个 impl；
`Inbound.msg` 是可选字段，不用可以永远 `None`。

**未验证**（实现时顺手验）：

- bot 给**用户发的消息**加 reaction（curl 阶段只验了 bot 给自己的消息加）。
- 群聊与私聊是否一致；对很旧的消息是否有时间限制（文档未写）。

## D25 · 微信通道的定位：对话入口，不是推送通道

**背景**：实测把额度模型钉死了（`WEIXIN.md` F10 / F16 / F17）：
**每条入站消息给 10 条出站，且不随时间恢复**；`bot_token` 与 `context_token` 都没有 24h TTL。
于是"对话"与"推送"是两种命运：

| 用法 | 上限 | 会枯竭吗 |
|---|---|---|
| 对话（用户说 → bot 答） | 每条用户消息重置为 10 | 不会 |
| 推送（用户不说 → bot 主动发） | 最后一次入站之后的余量 | 会，最多 10 条 |

**决定**：

1. **微信通道定位为对话入口**。用户问、bot 答；不承担通知、告警、日报这类单向推送。
2. **一轮 run 的出站预算按 1 条**（终稿）设计。没有编辑能力（`WEIXIN.md` F6），
   所以也别做"先发占位再改"——改不了，只会多花额度。
3. **不做状态反应**：协议没有 reaction 接口（F14），想表达状态只能发消息，
   而每条消息都是额度（对照 D24 的四态表情）。
4. **定时提醒不默认投微信**。真要投，只在"最后一次会话仍有剩余额度"时投一次，
   不重试、不补发；发不出去就只记日志，不当作失败告警。
5. **接入时 README 必须写明这条定位与额度约束**（作为该通道的 DoD 之一，
   见 `ROADMAP.md §5.13`）。否则用户会理所当然地把它当推送通道用，
   然后在第 11 条消息上莫名其妙地"静默失效"。

**理由**：

- 额度是"按对话续费"的，天然鼓励"一来一回"，惩罚"单向广播"；
- 10 条 ≈ 10 轮问答，对话场景下用户感知不到限制；
- 一旦拿它做推送，失败是**静默的**（`ret=-2 prepare failed`，界面上什么都没有），
  比报错更糟——用户以为发了，其实没发。

**代价**：

- 微信侧收不到主动通知；要提醒的人继续用 Telegram（或别的通道）。
- 与 `D24` 的取向一致：同一条通道在"状态回执"和"主动推送"上都不做，
  它就是一个老老实实的问答入口。

**反悔成本**：低。定位是文档与预算参数；真需要推送时，加一条"投递前检查余量"的策略即可，
不影响通道本身。

## D26 · 身份与记忆归属：配置写死、一人多账号、scope 跟人走

**背景**：`User ↔ Binding` 两层结构早就有（D16），但白名单还重复写在通道配置里，
记忆 scope 用的是**通道地址**。一人多账号（两个 TG 号 / TG + 微信）时会出现两个问题：
白名单要改两处、同一个人被当成两个人（各自的 `user:` 记忆互不可见）。

**决定**：

1. **白名单唯一来源是 `[identity]`**。删掉 `[telegram] allowed_users` / `[weixin] allowed_users`
   （非空直接报错，不做静默兼容），删掉 `default_user` 兜底。启动时 `[identity]` 为空直接拒绝启动。
2. **一人多账号 / 多人只是多写几条绑定**，不需要新概念。隔离仍是会话级（`{channel}:{addr}:{epoch}`）。
   **通道限定**：这条只在"平台允许一个 bot 服务多个账号"时成立。
   微信（ClawBot）**换一种形态**：一个 bot 只服务扫码的那个微信号，所以多人不是"一个 bot 加人"，
   而是**每人各绑一个 bot、各持一个 token**（`WEIXIN.md` §1）。
   实现方式：**一个凭据文件 + `accounts` 数组**（`weixin-login` 按 `user_id` 合并追加），
   通道 id 仍是一个 `weixin`——因为"一个 bot 只服务一个微信号"，回复时**按会话（openid）
   反查该用哪个 token**。每个账号独立长轮询、独立游标（`wx.buf:<bot_id>`），
   一个账号 `-14` 只停它自己。
3. **未绑定 = 未授权**：回一句「未授权」，**不跑模型**；同一地址**每小时最多提示一次**（防刷屏、防被当回音壁）。
   不做申请/审批流程（D16 的扩容路径保留为未来扩展）。
4. **记忆 scope 跟人走，不跟通道走**：`family` 或 `user:<user id>`。
   `remember(scope="user")` 由工具自己解析成 `user:<id>`，注入侧用同一个 id 查询。
   **与 channel 无关**：同一个人两个号、两个通道看到同一份个人记忆。
5. **谁决定 family 还是 personal：模型自己判断**。工具的 `scope` 参数保留，description 里写判据：
   "全家都适用的写 family；只跟某一个人有关的写 user"。

**修掉的旧 bug**：`remember(scope="user")` 原来写的是字面量 `scope="user"`，
而注入按 `user:<addr>` 查 —— 写进去的个人事实**永远读不回来**。现在两端口径一致。

**代价**：

- 未授权回复在微信上要花一条出站额度（但那是**对方那条消息刚开的**额度，不是主人的——见 `WEIXIN.md` U10）。
- 模型可能滥用 `family`（把私人信息写成共享）。单人家庭里无所谓；真要收紧就加"审批后升级 scope"，现在不做。
- `[identity]` 为空即拒绝启动：以前"配个 token 就能用"的裸跑方式不再可行。

**反悔成本**：低。scope 是数据，能改；白名单派生是一处函数。

## D27 · 提醒的投递目标：默认当前通道，可显式指定

**背景**：多通道并存之后（D26），提醒的 `targets` 原来是"这个用户的**全部**绑定"。
单通道时看不出问题；一旦同时开了 Telegram 和微信，一条"提醒我带伞"会**同时打到两边**，
而微信每条出站都吃额度（而且微信的定位是对话，不是推送，D25）。

**决定**：

1. **默认投当前会话所在的绑定**。这不是偷懒：你能建提醒，说明你刚在这个通道说过话，
   所以"当前通道"天然就是"最近活跃"的那个，不需要额外记录活跃时间。
2. `remind(channel = "weixin")` 可以显式指定；指定的通道不在该用户的绑定里时**报错并列出可用绑定**
   （不静默回落到默认，否则"为什么提醒跑到 TG 去了"会很难查）。
3. **只投一个目标**：`targets` 恒为一个元素，`message` 形态不再扇出。
   想同时提醒到两个通道，就建两条（或以后加 `channels=[...]`）。
4. `/reminders` 与 `reminders(list)` 显示「投到：channel · addr」——多通道下必须能一眼看出会发到哪。

**代价**：

- 少了"一条提醒投多处"的便利（真需要时两条任务即可，id 按内容哈希，不会互相覆盖）。
- 后台任务的空闲门 `last_active` 仍是**全局**的：A 在聊天会挡 B 的后台任务。
  单板单实例下这是有意的（有人在说话就别跑重活），多用户时算已知取舍，不为此加按人维度。
- 跨通道的"最近活跃"没有持久化：如果将来要在**没有对话**的情况下决定投哪里（比如系统级告警），
  需要补一张 `bind.last_active` 表；现在没有这个场景。

**反悔成本**：低。投递目标是 payload 里的两个字段，改回来是一行。

## D28 · 审批卡面向非程序员：模型必须解释，回复只要一个数字

**背景**：微信上发起审批时，卡片只贴了工具名和一长串命令，回执是
`/approve appr-1793414824767-0`。微信里长按只能全选整条消息、光标根本挪不动——
**id 打不出来也复制不了**，审批实际上没法完成。而且"lan_exec + 一坨 shell"对不写代码的人
等于没给信息。

**决定**：

1. **模型必须解释**。会触发审批的工具（`lan_exec` / `host` / `elevated` / `install_deps` /
   `publish_skill` / `remind`）在 schema 里带一个**保留字段**：
   ```json
   "_approval": { "why": "一句人话", "impact": "只读 / 写文件 / 装软件 / 向设备发指令 / 改自身配置" }
   ```
   `why` 与 `impact` 都是 `required`。内核在**执行前剥掉** `_approval`，工具看不到它。
   **每一个会触发审批的工具都要在 schema 里声明它**（并把 `_approval` 放进 `required`）——
   只在系统提示里列名单会漂：2026-11-04 的 `role` / `service` / `publish_playbook` /
   `rollback_playbook` 就是名单里没有、schema 里也没有，审批卡只能显示"模型未说明"。
   `tests/selfmod.rs` 现在断言这四个工具都声明且必填。
2. **卡片三段式**（顺序固定）：做什么 → 影响面 → 工具/命令（命令摘要 ≤200 字）。
   缺 `why` 时显示「（模型未说明这条要做什么）」，不假装有解释。
3. **短码审批**：同一会话同一时刻只有一条待审批（run 持会话锁、审批门串行），
   所以收到**完全等于** `1` / `2` 的文本就是"允许 / 拒绝"当前这条——**不跑模型、不花 token**。
4. 没有待审批时，`1` / `2` 是普通消息；审批超时后短码自动失效。
5. `/approve <id>` 保留为精确路径（Telegram 按钮、日志里复制用）。

**理由**：

- 审批的本质是"让人判断风险"。判断需要的是**意图 + 影响面**，不是 argv。
- 微信没有按钮（`Caps.buttons = false`），能用的输入通道只有文本，而文本输入的成本
  决定了"要不要打 id"。一个数字是这条通道上唯一现实的操作。
- 让模型写 `why` 而不是让工具猜：只有模型知道它**为什么**要跑这条命令；
  工具能做的是机械摘要（`approval_hint`），两者互补，卡片上都显示。

**代价**：

- 每次带审批的工具调用多两个字段（约 40 token）；
- `required` 意味着即使这次调用被 `grant=always` 预批准，模型也要填——多一点开销，
  换来的是"卡片永远不会缺解释"；
- 短码有误触可能：你正在回答别的问题、同时有待审批，顺手发个 `1`。
  概率低，且卡片上明确写了"回复 1"，可接受。

**反悔成本**：低。`_approval` 是可选字段，去掉就回到"只贴命令"；短码是一个拦截分支，删掉即可。

## D29 · 只发附件时先收着，等指令

**背景**：微信的图片**不能带 caption**（TG 可以）。用户发一张图过来，本意通常是
"我待会儿要让你干点什么"，但消息里没有文字——上一版直接把空文本 + 附件丢给模型，
模型就自己开始 OCR、复述图里所有文字，等于**抢跑**。

**决定**：

1. 入站消息**只有附件、没有文字**时：**不跑模型**，把附件暂存在内存里，回一句
   「📎 收到 N 个附件。要我做什么？（描述内容 / 提取文字 / 打印）直接说一句就行。」
2. 用户随后说话时，把暂存的附件**挂到那条消息上**再正常跑——所以"发图 → 说'打印这个'"
   是一个连贯动作，不需要重发。
3. 暂存上限：**4 个附件 / 10 分钟**，超时或超出就丢弃（不做持久化，重启即失效）。
4. 这条规则**与通道无关**：TG 上没有 caption 的图片也走同一条路（行为一致）。

**理由**：

- 附件本身不是指令。模型看到图 + 空指令，只能靠猜——而"猜"在这个系统里是最贵的错误。
- 微信没有 caption 是平台限制，改不了；能改的是我们收到之后做什么。
- 回执只花 1 条额度，比"跑一轮 30 秒的模型再让它重新问"便宜得多。

**代价**：

- 用户必须补一句文字（对"就想让它直接描述"的场景多一步）。
- 暂存是进程内内存：重启会丢（此时用户需要重发，或直接说指令）。
- 多花一条回执额度。

**反悔成本**：低。判据是 `is_bare_media()` 一个函数，去掉就回到"直接跑"。

## D30 · 审批分两类 + 家人零审批（**已实现，待上板**）

> 状态：**P0–P4 已实现（开发机）**，等上板复核（`SBC-VERIFY §13`）。本节是 2026-11-02 的定稿设计，
> 同日按"家人零审批"口径修正过两次：
> ① 家人**不收到任何审批卡**（含 Confirm），歧义改为普通对话反问；
> ② `lan` 的"命名动作"泛化为**命令条目表**，独立成 D31，本节只留指针。
>
> 已落地：`[identity] owner` + `ActorRole`、按角色的运行时判定（`policy::decide`）、
> `RunStatus::Blocked` 与 runner 真终止、三条批准入口的批准人校验。
> 已落地全部五段。剩余是上板项（真实打印机、纸型名、通道实测），见 `SBC-VERIFY.md §13`。

**背景**：三个真实瓶颈——(1) 通知渠道不可靠（TG 要开代理、微信只能被动回）；
(2) 家人使用的动作（打印、查状态）每次都弹审批；(3) 审批卡是一长串 shell
（`lp … ; sleep 3 ; lpstat … | head -1`），非程序员只能无脑点"允许"。
同时，软拒绝会诱导模型换路径重试，把 token 烧在"绕过限制"上。

**决定**：

1. **身份**：`[identity] owner = "<user-id>"`，其余已绑定的人一律是 **member**（`ActorRole`；
   别叫 `Role`——消息角色已占用该名）。未绑定的 actor 按 member 处理（fail closed）。
   owner 与 member 的差别**只有一条：谁能批准**。member 拿不到任何审批卡，所以给家人的
   可用面必须靠"构造上有界"的东西支撑：沙盒 / 出网 / 宿主观测 / `who = "anyone"` 的
   命令条目（D31）/ 声明了 `member_safe` 且能自证"只作用于发起者本人"的工具（目前只有
   `remind`）。

   **运行时判定顺序**（不可颠倒；数据面 `Verdict` 仍是三值，`GateDecision` 是四值）：

   ```
   Deny（domain = deny，对所有人不变，这是天花板）
     → 命令条目命中 + 参数全在域内 → Allow        // 条目是 Ask 的答案，不是新授权层（D31）
     → member 且 domain ∉ {sandbox, outbound, host_observe}
         且（未声明 member_safe 或这一条未自证有界）且未命中命令条目
         → Blocked{need_owner}                    // 终态：记提案、通知 owner、不建审批行
     → Ask（只对 owner；member 到不了这里）
   ```

   为什么条目在角色上限**之前**：否则家人连打印都不成立（`lan` 默认 ask，而家人不能批）。
   为什么 `Deny` 在条目**之前**：D22 的天花板是"`skip_approval` 只能把 ask 放成允许"，
   条目同样不能把 `deny` 放开；把 `[policy] lan = "deny"` 写下去，该域条目整批失效。
   `member_safe` 必须是 fail-closed 的显式声明（默认 false），且只能由数据/自指条件判定，
   不得有自由裁量。
2. **审批分两类**（同一张表加 `kind`，不建两套子系统）：

   | | `Permission`（权限批准） | `Confirm`（单次确认） |
   |---|---|---|
   | 谁批 | **只有 owner** | **只有 owner**（原设计"发起者本人"已修正） |
   | 批准后 | 只改命令条目表，**不执行任何动作**（D31） | 执行那一次动作 |
   | 请求方等吗 | 不等（该 run 以 `Blocked` 终止） | 等（短 TTL，默认 10 分钟） |
   | 过期 | 提案作废 | 动作作废，不重放 |

   **修正理由**：家人没有计算机基础，卡片上的 argv 他看不懂——看不懂的确认等于无脑点允许，
   比不给卡更糟。所以 `Confirm` 不再给家人；家人遇到"必须确认"的情况走**普通对话反问**
   （agent 自己说不准，问一句"是明天早上八点吗"），这既不是审批、也不落审批表。
   三条批准入口必须校验批准人：`Permission` 要求 owner，`Confirm` 要求 owner；
   不匹配时不改状态并回一句"这个需要更高权限的账号来确认"。

3. **`lan` 不再接受 `sh -lc` 作为免审批路径**：免审批只能走**命令条目**（D31）。
   条目给 `argv` 模板 + 封闭参数域，进程按 `Command::new(argv[0]).args(..)` 启动，
   **不经过 shell**；参数越界直接拒绝，不落到沙盒里才发现。`lan_exec` 保留为 owner 的
   逃生口（逐条确认），描述里写明"有对应条目就用条目"。
   首批条目：`print_file` / `printer_status` / `supplies` / `printer_list`。
   泛化到 `host`、以及为什么 `install` 永远不进条目表，见 D31。
4. **扩张由 agent 提议、owner 一次批准**：新增纸型（A4/B5/相纸）、换打印机都走
   `capability(action="request", kind="command")` → 一张显示规范化条目 + **单独一行
   `env` / `who`** 的卡 → 批准后**由内核**写入 `commands.d/<name>.toml` 并热加载。
   agent 不写盘（它拿不到该目录的写路径），也不能自批；详见 D31 §8–§9。
5. **未授权 = 终态**：表外条目、参数越界、member 触到域上限，一律 `Blocked`
   （结构化：缺什么 + 已授权什么 + 下一步），kernel **真正结束该 run**，prompt 明确
   "不要换路径重试"。最坏烧一轮，不是十分钟。
   > 现状不是这样：拒绝只写 `denied` 然后 `return Ok(())`，run 继续，模型会换写法再试。
   > `RunStatus` 目前也只有 `Done`/`Failed`/`Cancelled`，三态化是 P0.5 的全部内容。
6. **不做异步待办与自动续跑**：几小时后执行往往已无意义（提醒过点、纸已手工打）。
   批准改变的是**未来能力**，不是过去那一次。
7. **提醒默认不审批**（已实现）：工具按"目标就是发起者本人 + 绝对时间在未来"自证有界，
   直接回"已排期 <本地时间>"；只有"明早/下周"这类**语义**歧义才反问，且走普通对话，
   **不建审批行、不发卡**。这条现在是**必需**而不是优化：家人不能批，`remind` 若仍
   走 `SelfModify` 的 Ask，家人就完全没法设提醒。

   免审对**所有形态**、**所有主体**成立（`Tool::preapproved_for` 只做数据判断：
   目标自指 + 时间可解析且在将来）。四种形态：

   | 形态 | 到点做什么 |
   |---|---|
   | `message`（静态） | 只发这句话 |
   | `skill`（钉住脚本） | 跑已安装技能（离线沙盒），不过模型 |
   | `skill` + `polish` | 先跑脚本，**再跑一轮模型**加工输出 |
   | `text` | **跑一轮模型**（带着工具面） |

   **到点那一轮不进审批**（`InboundKind::Scheduled`）：
   - 遇到 `Ask` 的步骤**不发卡、不等人**，直接跳过，并立刻给 owner 一条
     "有条定时任务需要审批"（同一会话 + 同一工具只报一次）；
   - 整轮结束不是 `Done`（失败 / 被挡 / 取消）→ 再给 owner 一条结果通知。
   理由：定时任务跑在凌晨，发卡只会白等 10 分钟超时、还把整轮拖垮；失败也不能无声无息。

   后两种会跑模型，于是有人问"家人能不能靠它绕过审批"。答案是不需要拦：
   到点那一轮的主体会被**继承**（`actor` = 创建者），所以能力面不会超过他本人在场时的
   范围；拦掉形态只会让家人永远用不了需要模型的提醒。无人值守这件事用**可见性**管：
   家人建成模型形态的任务后，owner 会收到一条通知（任务内容 + 下次时间 + 怎么取消），
   只通知一次，不挂卡、不等待。

   理由：`text` 形态等于排了一个"几小时后执行任意工具动作"的无人值守任务；家人能建它，
   就把"当时没人在场"变成了绕过审批的通道。成员把已有提醒 `update` 成 `text` 形态同样拦。
8. **家人路径**：**不给审批卡、不给按钮、不挂起**。被 `Blocked` 时的回复是
   "这个我现在没有权限做，已经记录下来了；你可以先自己处理，或者等有权限的人回来"。
   （文案里不写身份称谓，见 `GLOSSARY.md` §G.9。）
   owner 侧只在**同一形状重复被挡**（≥2 次/24h）时才收到一条提案，避免被当成日志。
   家人能做的事只有：沙盒内的事、出网取资料、看宿主状态、`who = "anyone"` 的命令条目
   （打印/查墨量），以及回答 agent 的反问。

**理由**：免审批不能靠"人看过"，要靠**构造上效果有界**（固定 argv + 封闭参数域）。
人的角色从"逐次审命令"变成"一次性批形状"；agent 负责发现与维护数据，但不能自授权。

**非目标**：RBAC / 多租户；对任意 shell 做语法白名单（做不对）；用频率配额代替审批
（只是把问题推后）；异步审批 + 续跑。

**代价**：
- `verdict` 保持三值（数据面），但 gate 要输出四态 `GateDecision` 并贯穿 actor/runner/两处 gate；
  `Tool` 增一个 fail-closed 的 `member_safe()`。
- `lan` 从"万能 shell"变成条目表，遇到表外需求只能提 proposal（多一次往返）。
- 审批表增 `kind` / `requester`（schema V6），内核多一条"批准后写数据文件"的路径
  （写盘不在事务里，靠两条 journal 事件与 hash 校验兜底，见 D31）。
- 家人能力面被压窄：raw `host` / `lan_exec` / `install_deps` / 发布技能一律不可用。

**反悔成本**：中。命令条目表与审批分类都是数据/局部代码，可回退；但白名单一旦对家人开放，
撤销需要重新训练使用习惯。

**落地顺序**：P0 身份与批准人校验 → P0.5 `Blocked` 三态 → P1 命令条目表 + `lan_command`
（D31）→ P2 `capability` 提案与内核安装 → P3 提醒去审批 → P4 家人 UX →
P5 触发式（`host_command` / `commands.d` 权限升级 / 发现动作）。

## D31 · 命令条目表（`commands.d`）：把"免审批"变成数据（**已实现，待上板**）

> 状态：**P1 + P2 已实现（开发机）**：`env="lan"`、四个条目、审计、`capability` 提案与
> 内核安装/删除（`Permission` 审批 + 指纹校验）。`host_command` 属 P5。D30 §3 的"`lan` 命名动作白名单"是本条的 `env="lan"` 特例，
> 两者不要各写一套。实现顺序见 D30 末尾。

**决定**：

1. **形态**：一条**命令条目**（Command Entry）= 名字 + 执行环境 + argv 模板 + 一组封闭参数域。
   落盘 `commands.d/<name>.toml`，**一文件一条**：好审（一行 diff）、好回滚（删文件）、
   好热加载（单文件 mtime）、不会多写者合并。

   ```toml
   # commands.d/print_file.toml
   env = "lan"                    # lan | host（install 永不进表，见 §12）
   argv = ["/usr/bin/lp", "-d", "{printer}", "-o", "media={media}", "{file}"]
   timeout_ms = 20000
   who = "anyone"                 # owner（默认）| anyone
   [params]
   printer = { enum = ["HP-DeskJet-2720", "Brother-L2350"] }
   media   = { enum = ["A4", "B5", "photo_4x6"] }
   file    = { file = ["/ws"] }
   ```

2. **按 env 分工具，不引入"按参数决定域"**：v1 只有 `lan_command(name, args)`，
   将来 `host_command`。`Tool::domain()` **保持静态**——动态域会让
   `effect/lane/tier` 只改半个契约；更糟的是 gate 批的条目与 execute 解析的条目可能
   不是同一条（热加载、改名），审计无法自证。
   **代价要认**：同一个工具内所有条目共用 `effect()` / `lane()` / `tier()`，所以
   `lan_command` 一律 `External`（崩溃后不自动重跑）、车道 `io`、`tier = 1`（子 agent 不打印）。
   只读条目因此也不重跑——可接受：重跑一次查询很便宜，误重跑一次打印很贵。

3. **授权语义**：条目是 `Ask` 的答案，**不是新的授权层**（等价于
   `[host.path] approval = "always"` 换来的免问）。`deny` 是天花板：某域配成 `deny`
   时该域条目整批失效。`who = "anyone"` 只表示"这一条不打扰任何发起者"，
   **不表示跨过 member 的域上限**——member 能用的条目只能是 `env = "lan"`。

4. **参数域只有四种**（v1）：`enum` / `file`（限定根；执行时 canonicalize，
   拒绝符号链接逃逸）/ `int { min, max }` / 封闭 `pattern`（ASCII 字符类，
   形如 `{ chars = "A-Za-z0-9 _-", min = 1, max = 12 }`；"任意包名"这种
   "选择代码"的开放域不算封闭）。
   **`file` 的根 v1 只有 `/ws`**：`lan` lane 不挂 `/media`（那条 lane 同时跑
   `lan_exec`，为打印放开整块相册不值）。要打聊天里的图片，先让沙盒 `cp` 到 `/ws`
   —— 两步都对家人免审（沙盒默认 allow），用户无感。把 `/media` 挂进 lan 是 P5 的
   一次显式取舍，不是顺手加一行。
   **不做"由发现动作填充"**：模型传值 = 域不封闭，内核缓存 = 隐式状态。
   `printer` 用 `enum`，换打印机就改一行条目。

5. **解析一次、带 hash**：gate 解析出 `ResolvedCommand { name, env, argv, hash }`，
   execute 只认它；审计记 hash。这样热加载竞态不会变成"批准 A、执行 B"。

6. **清单注入 system**：每轮把"已生效条目的签名"（名字 + 参数域，如
   `print_file(media: A4|B5, file: /ws 下的路径)`）追加进 system，并写明"有对应条目就用它"。
   不注入的话模型只知道 `lan_exec`（永远要审批）——2026-11-03 板上真实事故：问打印机状态
   依然弹审批卡，因为模型压根不知道有条目可用。签名**不暴露 argv**。
7. **审计**：每次执行写一行 `lan-access.jsonl`（条目名、解析后 argv、hash、exit、ms）；
   `capability(list)` 显示条目来源、mtime、条数，以及**坏文件是哪一条**。

8. **写入路径：agent 不写盘**。`capability(action="propose_command", command={...})` 渲染出
   **规范化条目**并先自校验，然后只写**草稿**（`<config>/capabilities/commands/<name>.toml`）；
   运行结束后内核把它转成 `approval(kind = Permission, requester, entry_name, entry_hash)`，
   并给 owner 的每个绑定发一条带 `/approve <id>` 的通知。owner 批准后由**内核**执行
   `validate → tmpfile → fsync(file) → rename → fsync(dir)`，成功才记
   `command.installed { name, hash, approval_id }`（删除记 `command.removed`）。
   **不在 `begin_write` 事务里写文件**（不变量 6）；写成功后清草稿。
   安装前还会核一次指纹：**草稿在批准后被改过就拒绝**，避免"批的是 A、装的是 B"。
   通知里**只显示提案人写的一句人话 `summary`**（例如"打印 `/ws` 里的文件，纸型 A4/B5"），
   不显示 argv、`env`、`who` 或指纹——这些只进账本与日志。理由见 D30 的文案规则：
   不写代码的人看不懂 argv，"看懂后果"比"看到原文"更重要。

9. **只增删、不改**：重名一律拒绝（否则"批准的"和"生效的"可能不是同一份内容）；
   删除走同一条提案路径（`capability(action="request", kind="command", remove="name")`）。

10. **目录权限与 `services.d` 相同**：`0770 root:chuan`，加入强制遮蔽列表。
   信任假设写明：本设计信任 `PROTECTED` 遮蔽——若 agent 拿到任意宿主 `rw` 路径授权，
   表可被绕过写。主人已知并接受这一点；"给 `hostd` 加一个只写该目录的窄动词"是另一条路，
   触发条件见 §12。agent 侧只有"经 `capability` 提案"这一条路。

11. **可预授权的判据**（一条条目能免审批的必要条件，换哪个 env 都适用）：
    ① `argv[0]` 是绝对路径（不走 PATH，否则可被同名程序替换）；
    ② 其余参数取自封闭集，或效果由构造有界（根约束下的文件、区间整数、设备/纸型枚举）；
    ③ 效果可恢复、不破坏共享状态；
    ④ 目标不是授权面自身（`commands.d` / `chuan.toml` / secrets）；
    ⑤ `pattern` 只接受封闭字符类。

12. **范围与触发条件**：
    - `lan`：v1 做（打印四条目）。
    - `host`：`host_command`，判据同 §10，优先只读类（`journalctl -u <unit>`、`systemctl show`）。
      注意：`host` 的"任意 argv"不因为叫条目就变得安全——必须是"绝对前缀 + 封闭参数"。
    - `install`：**永不做条目**。包名是开放域（选包 = 选代码，maintainer scripts 是 root 执行）。
      触发条件：只有"固定签名/固定哈希的本地包源"时才重新讨论；在那之前装依赖永远逐条批。
    - `host_elevated`：触发条件是"`hostd` 直接读同一份 `commands.d`（同解析器、同 mtime、
      fail-closed），且条目必须带 `snapshot_argv`"。风险主要在**语义**不一致
      （`[[host_elevated.grant]]` 是开尾 argv 前缀，条目是封闭参数），不只是两份文件。
    - `self_modify`（`publish_skill` / `role` / `service`）：不进表——它们不是 argv 形态。
      `remind` 按 D30 §7 直接从 Ask 里拿掉，也不要塞进表。

13. **失败语义**：单个文件解析失败只废该条（与 `paths_error` 同款）；
    `capability(list)` 与 `Blocked` 文案要点名是哪一条；一个文件的语法错误不影响其它文件。

**理由**：免审批只能靠"构造上效果有界"，不能靠"人看过"。而"有界"这件事本身是**数据**：
固定 argv + 封闭参数域，换纸型/换打印机只改一行。人的角色从"逐次审命令"变成"一次性批形状"；
agent 负责发现与维护数据，但不能自授权。

**非目标**：任意 shell 的语法白名单（做不对）；`from = 发现动作`（v1 不做）；
条目运行时改参（要改就删了重建）；异步审批与自动续跑（D30 §6）。

**代价**：多一个数据目录与一套加载/校验（与 `GrantsCache` 同构，但按文件失效）；
打印机出局后要记得删条目；`who = "anyone"` 写错等于给家人开口子（默认 owner 收窄了这一点）。

**反悔成本**：低。删掉 `commands.d/` 即回到"全部逐条审批"；`lan_command` / `host_command`
是独立工具，去掉注册即可，不牵连 `lan_exec` / `host`。

**验收**：
1. 四条 `env = "lan"` 条目对 owner 与 member 都零卡执行；参数越界与表外条目都是
   `Blocked`，且账本里该 run 的 **turn 数 = 1**（"没换路径重试"可数）；
2. `command.installing` 之后 `kill -9`，重启按 hash 复核：一致补记，不一致标失败并通知；
3. 单个文件写坏只废该条，其余照常，`capability(list)` 指出坏在哪；
4. 把 `[policy] lan` 改成 `deny` → 该域条目整批失效（`deny` 是天花板）；
5. member 跑 `env = "host"` 的条目（若存在）→ `Blocked{need_owner}`，owner 收到提案，
   且审批表里没有为 member 建行。

## D32 · 二进制取件走服务工具（`http(save_to)`），临时凭证不进上下文

**背景**：从配置好的服务取文件本体时，端点常返回 3xx 跳到**带签名的临时直链**。
此前只能把这条 URL 交给模型拼进 `lan_exec` + curl：每次一次审批（`lan` 是 `Ask`），
临时凭证进了 tool_calls 与账本，而且端点路径规则只能靠试错。

**决定**：`http` 服务工具增加 `save_to`。命中 3xx 时**由宿主跳一次**：目标主机必须在该服务的
`redirect_hosts` 白名单里（`*.example.com` 通配），第二跳**不带任何鉴权头**，响应体流式写
`/ws/<save_to>`，返回 `{path, bytes, sha256}`。临时凭证与响应体都不进上下文、不进日志。
上限 512MB；`content-type` 是 JSON/文本时直接报错（防误加参数把接口结果写进文件）；
只允许 GET。**上游非 2xx 属于环境问题而不是参数问题**：按 `Unavailable` 报，并把响应体前
300 字节带出来——否则"响应不是文件"会盖掉上游真正的原因（真实踩过：alist 的
`401 sign mismatch` 被翻译成"你的参数不对"，模型转而去猜百分号编码和 `lan_exec + curl`）。

**时间维度与 API 分开**：`reqwest` 的 `.timeout()` 是总超时（建连到读完响应体），拿它卡下载
跟 512MB 上限自相矛盾——22MB 在 20KB/s 上就会"下到一半就断"，看起来像网络问题。因此下载用
独立的 client：**不设总超时**，只设空闲超时（连续 60 秒没有新字节才断）；普通 API 调用保持
总超时 30 秒。判死的依据是"还有没有进展"，不是"总共花了多久"。

**第二跳可以补头，但按目标主机绑定**：有的网盘对直链有 UA 要求（百度 >20MB 必须
`User-Agent: pan.baidu.com`），而同一个 alist 后面可能同时挂着阿里云和百度——把百度的 UA
发给阿里云就是错的，挂在 service 上也管不住"跳去哪"。所以配置写成"**跳到这个主机时补这些头**"：

```toml
[[services.alist.redirect]]
hosts = ["*.pcs.baidu.com", "*.baidupcs.com"]
headers = [["User-Agent", "pan.baidu.com"]]
```

三条约束保证边界不扩大：① 目标主机必须先过 `redirect_hosts`，规则只在命中的主机上生效；
② 值是**字面量**，不做 `{token}` 渲染，结构上带不出凭据；③ `Authorization` / `Cookie` 这类
名字直接拒绝。附带一条：`service` 工具**拒绝同名重加**已带下载边界的服务——它只写
base/token/header，重加会把这些清空、并让 services.d 片段在下次启动盖掉 chuan.toml。

**理由**：边界不扩大。不新增"任意 URL 下载"工具，也就没有 SSRF 面：域名来自配置，
目标主机来自白名单。鉴权仍只在宿主侧（不变量 9/14）。`outbound` 域默认免问，
所以这是"既定出网能力"的一种形态，不是新的授权面。

**非目标**：不跟随重定向链（>1 跳拒绝）；不做断点续传；不做任意 URL 直链下载
（真需要时再讨论 `[download] allow_hosts`，先有真实用例）。

**反悔成本**：低。删掉 `save_to` 参数即回到"元数据走服务、本体走 lan"。

**验收**：
1. 302 → 白名单主机：文件字节与响应一致，sha256 可核对，结果与日志里都没有临时凭证；
2. 302 → 非白名单主机：`NotPermitted`，磁盘不留文件；
3. 2xx + JSON/文本响应误加 `save_to`：`InvalidArgs`，提示去掉参数，**并附响应体前 300 字节**；
4. 非 2xx（含上游自己回的 JSON 错误）加 `save_to`：`Unavailable`，消息形如
   `下载失败：HTTP 401 · {响应体前 300 字节}`——状态码与原因都不许被"响应不是文件"顶掉；
5. 下载路径的审计日志只记 query 键、不记值（`?sign=…` 这类签名等于取文件的凭证）；
6. 慢响应（总耗时超过 API 总超时）加 `save_to`：能下完；同一个响应不带 `save_to`：按
   `Unavailable` 报超时——证明下载不吃那 30 秒；
7. 不带 `save_to` 时行为与改动前完全一致。

## D33 · KB 第一版：原件 + 页 + FTS，不建新表

**决定**：
1. **原件**按 sha256 存进文件库（`files/<sha256前16>/<name>`，与 `keep` 同一布局），是唯一不可重建的东西；
2. **每页一条 `kb.page` doc**（`payload.text` 被 `docs_fts` 索引），**来源一条 `kb.source` doc**；
   id 内容派生（`kb:<sha>` / `kb:<sha>:p<N>`），重复入库等价于覆盖；
3. **格式解析不写进 Rust**：PDF / Word / 扫描件由 agent 用它装好的库或系统工具抽成
   "按页切好的 UTF-8 文本"，作为 `pages_file` 交给 `kb_ingest`。缺库就由它自己申请安装
   （`install` 域，逐条审批）。KB 只存原件、索引正文、取件——否则每加一种格式都要改一次 Rust（不变量 15）；
   **出图也不内置**：`kb_file` 只把原件放进 `/ws`，要图片/裁剪/节选由 agent 用自己的工具做，
   再用 `send_file` 发出去——渲染器和解析器一样是领域能力，换格式就变；
4. 不新增表、不改内核：只用 `doc_writes` / `DocReader` / `Retriever` / `ExecutionEnv` 四个既有端口。

**理由**：`docs` 早就是 KB 的索引位（D8 的 `kind="file"`）；页文本是可重建的派生数据，先复用现成的
trigram 索引比为一个尚未验证的规模去设计投影表更划算。抽取不进内核，是因为"支持哪种格式"
是领域问题：换教材/换来源就会变，而 KB 的存储与检索不会。

**代价**：页文本会进账本（一本 200 页约 400KB）；`docs` 行数随书增长；
正文质量取决于 agent 抽得怎样，所以 `kb.source` 记 `text_from`（如 `pdftotext` / `python-docx` / `ocr`），
扫描件抽不出字就明确失败，不猜内容。

**重复入库的语义（2026-11-06 修正）**：以**新抽取为准**。
页数变少时，超出新页数的旧页在同一次事务里删除（`DocOp::Delete`，页号连续、探测到空洞为止，
历史遗留的孤儿也能清）；正文摘要（`text_sha`）变化时一并删除旧的结构索引（页锚点必然失效），
内容没变（幂等重入）则保留。`kb_forget` 同样是"删页 + 删结构 + 删来源"一次提交，不再逐条独立事务。

**触发条件（什么时候拆表）**：语料过万页、需要按来源批量删除/重建、或账本体积成为备份负担时，
再上 `kb_page` / `kb_chunk` 投影表 + `chunks_fts`；`Retriever` 接口已预留，`doc_id` 形态不变。

**验收**：
1. 入库后**重启服务**仍能 `kb_search` 命中并 `kb_read` 取回整页；
2. 同一份文件重复入库不产生副本，返回同一个 `kb:<sha>`；
3. 正文文件为空、或抽不出文字时明确报错，不产生半截索引；
4. `kb_file` 放出来的原件与入库前逐字节一致，路径可被沙盒里的工具直接使用；
5. 取不到原件（被删/移走）时给可读错误，不返回空路径。

## D34 · 结构索引：节点树 + 确定性集合运算，不做 TOML profile

**背景**：「第一单元田字格生词」「第一单元要听写的词」这类问题不是全文检索能答的，
需要"资料是怎么组织的"这层信息，以及跨资料做并集/交集。

**决定**：
1. 结构存成一条 `kb.outline` doc（id `kb:<sha>:outline`），内容是**扁平节点数组**：
   `{id, type, label?, parent?, page?, attrs?}`。`type` 完全开放（单元/课/栏目/条款…），
   由 agent 自己定义并在 playbook 里写清楚含义。
2. 结构输入有两条路：小结构直接给 `nodes`；**几百个节点以上必须给 `path`（`/ws` 下的 JSON 文件）**——
   让模型内联几万 token 的 JSON 是不可行的（生成端会超时或烧光回合，2026-11-05 实测：908 节点 / 84KB 从未写成功）。
3. `kb_select` 只做确定性运算：`match{type,label,label_contains,attrs,under[]}` 过滤，
   `field` 投影，跨来源 `union` / `intersect`，每来源内部去重、保序。
   `under` 是**有序祖先条件**（在祖先链里按序匹配，允许中间还有别的层级）。
4. **不做声明式 profile（TOML/JSON Schema）**：「这一类资料有哪些字段、怎么找」是领域知识，
   写成 schema 就等于把领域逻辑挪回 Rust。它的载体是 **playbook**（D23）：给未来自己看的文字，
   agent 写、主人确认、覆盖留备份。

**理由**：结构抽取仍由 agent 完成（它可以错、可以改），但**集合运算不能交给模型心算**——
听写清单错一个字就废。把"抽"和"算"分开，前者放宽、后者收紧。

**代价**：结构写错时 `kb_select` 会给出空集（错误信息里带条件与来源，便于自查）；
`label` 精确匹配，写法不一致就取不到，所以提供 `label_contains` 兜底；
节点上限 5000、整份 ≤1MB。

**非目标**：不做结构版本管理（重写即覆盖）、不做自动从正文推断结构（那是 agent 的活）、
不做跨来源的实体消歧（"鸟"和"小鸟"算两个，除非 agent 在 attrs 里给同一个 `key`）。

**验收**：
1. 写入结构后 `kb_outline` 能按缩进看全树，页号可见；
2. 同一单元下的条目能被 `kb_select` 取出（`under` 只需写 unit 一层）；
3. 两份来源 `merge=intersect` 得到交集，`union` 去重后保序；
4. 写坏节点（父不存在 / id 重复 / id 带斜杠）立刻拒绝，不落库。

## D35 · 自改事务：原子写 / 备份 / 回滚 / 回收站 / 记账，五处统一

**背景**：agent 能改自己的五个地方，实现方式各不相同：
技能有 dry-run + 5 版备份 + 回滚；命令条目有 hash 复核 + `command.installed` 事件；
服务与角色则**直接 `write`**（断电留半截）、**删除即消失**、账本里只有工具参数；
规范（playbook）备份无限增长。同一件事（"我改了自己"）有五种可靠性水平。

**决定**：抽 `capabilities/src/selfmod.rs`，只统一**事务语义**：
1. `write_atomic`：tmp → fsync → rename → fsync(dir)。服务/角色/规范全部改走它；
2. `backup_file` + `prune_backups`：覆盖前备份，**统一保留 5 版**（技能的目录级备份沿用原逻辑）；
3. `newest_backup`：回滚取最新一份，**回滚动作本身也先备份**（可逆）；
4. `trash`：删除进 `.trash/`，不真删，回执里告诉用户怎么捞回来；
   **回收站有有效期**（`[trash] keep_days`，默认 30 天，0 = 永不清理）：
   启动时与每 6 小时按 mtime 清理 `files/.trash` 与 `<config>/*/.trash`——留着是为了"改错了能退"，
   不是为了永久存档；
5. `record`：每次变更落一条 doc（`skill` / `service` / `role` / `playbook`），
   带 action / sha256 / bytes；命令条目保留 `command.installed` 事件，不重复记。

**不统一的东西**（有意为之）：
- **校验强度**：命令条目要 argv 形状、参数域、hash 复核；规范只是文字。用同一把尺子只会两头都错；
- **工具名**：`publish_skill` / `publish_playbook` / `service` / `role` 是模型可见的语义，合并会破坏已有提示词；
- **生效方式**：技能/角色/规范立刻热加载；`services.d/` 只在启动时读，回滚后要重启（回执里明说）。

**非目标**：不动 `Tool::approval_hint` 的签名（审批卡读不到 `/ws` 草稿，做不了真 diff；
要做得改公开契约，单列）；不做跨载体的统一事务日志文件（账本已经是那个东西）。

**代价**：多一层间接（读取 `selfmod`），每个工具要维护自己的备份目录；
回收站需要主人定期清理（默认不自动删）。
**部署约束**：落在 `<config>/` 下的可写目标，必须同时出现在 unit 的 `ReadWritePaths`
（`ProtectSystem=strict` 下 `/etc` 只读）；目录权限用 `0770 root:<服务组>`。
2026-11-04 实测踩过：`playbooks/` 是 `0750` 且不在 `ReadWritePaths` 里，
`publish_playbook` 写临时文件被拒——权限看着对，实际是 `EROFS`。

**验收**：
1. 服务：add → 改 → rollback 回到旧 base → remove 后文件进 `.trash/`，四步各有一条账；
2. 角色：add → 改模型 → rollback 同时恢复 toml 与提示词（同一代），remove 两个文件都进回收站；
3. 技能/规范：覆盖留备份且最多 5 份，rollback 可再回滚；
4. 断电（`kill -9` 在写盘中途）不会留下半截 TOML。

## D36 · 上下文预算按 token 算，并把 system 与工具说明扣掉

**背景**：`context_budget_tokens=24000` 以前被换算成 `字符数 = token × 3`（英文经验），
而且只用于裁剪历史——system 指令、25 个工具的 JSON schema、当前消息都不占这笔账。
中文实际是"1 字 ≈ 1 token"，于是一边高估容量（3 倍）、一边漏算固定开销，
长对话很容易顶到模型窗口，表现为供应商返回 **HTTP 400 context length exceeded**。

**决定**：
1. `context::select` 改成按 token 估算裁剪；`estimate_tokens` 采用 CJK 感知的粗估
   （CJK 1 字 ≈ 1 token，其它 ~4 字符 ≈ 1 token）。不引真分词器：这里只决定"裁多少"，宁可保守。
2. `context_budget_tokens` 语义改为**一轮的总预算**：历史预算 = 总预算 − system − 工具 schema −
   1024 预留（当前消息与输出），下限 1000。
3. 供应商 400/413 中属于"太长"的那一类单独识别为 `EngineError::ContextOverflow`，
   回一句可操作的提示（把长材料放文件、按文件读），不再把裸 400 甩给用户。

**非目标**：不做精确分词（要维护各家的 tokenizer）；不自动压缩历史（那是另一件事，ROADMAP 另有条目）；
不加 `[engine] context_window`（模型窗口仍由配置的预算兜住，需要时再加）。

**验收**：
1. 纯中文长对话不再因为"看起来没超"而撞 400；
2. 系统指令与工具 schema 变大时，历史预算相应减少；
3. 供应商报"context length"时，用户看到的是"把材料放进文件"的下一步，而不是 `http 400`。

## D37 · 后台任务收尾：全部完成时唤醒父 agent，而不是只推一条消息

**背景**：后台任务完成时只 `reply` 一条"⏱ 后台任务完成"，不触发模型。父 agent 要等用户
下次开口才可能看到结论；而会话上下文可能已经被别的聊天挤掉、或被 `/new` 换了 epoch，
于是"派出去就不管了"的观感很真实。

**决定**：
1. 完成通知**升级为一次唤醒**：`[agents] resume_on_done`（默认开）。合成一条 `InboundKind::Resume`，
   正文包含**原任务 + 状态 + 结论 + 待父执行 + 子会话 id**（因为子 agent 的报告是写给接手的 agent 看的）。
2. **同一批只唤醒一次**：`pending` / `running` 全清空才唤醒；A/B 同批只在最后唤醒一次。
   已上报的任务在 doc 上标 `reported=true`，不会重复带出。
3. **落到当前 epoch**：唤醒时重新读 `conv.epoch:<channel>:<addr>`，`/new` 之后也能收到；
   不写回任务派发时的旧会话。
4. **不链式**：由唤醒产生的 run 所派的任务标 `notify=false`，完成时只通知不唤醒。
5. 唤醒的 run **不是** `Scheduled`：人在场，审批照常发卡（子 agent 自己按 member 判、永远不能批）。

**理由**：子 agent 的工具面窄、结论是"给接手的人看"的；只有父 agent 亲自过一遍，
结论才会变成动作或一句人话。这一轮 token 比"用户回来发现什么都没发生"便宜。

**代价**：每次收尾多一轮模型调用；唤醒消息会占一次用户可见的回复。所以给开关，默认开。

**验收**：
1. 单个后台任务完成 → 父 agent 自动接着做/汇报，消息里能看到原任务与子结论；
2. 同批两个任务（A/B）只唤醒一次，且两份结论都在；已上报的不再重复；
3. `/new` 之后任务完成 → 唤醒落在新会话，回复出现在当前对话里；
4. 唤醒后父 agent 再派的任务，完成后不再唤醒（无链式）；
5. `resume_on_done = false` → 回到"只推通知"。

## D38 · 卡住判定要区分"模型在等"和"工具在跑"

**背景**：actor 的卡住检测是"180s 没有任何事件就取消整轮"。但**工具执行期间模型不吐事件**：
前台 `delegate` 跑十分钟、`exec` 跑几分钟，都会被判成卡住，父 run 连子 agent 一起被杀
（2026-11-04 真实事故：26 课全量对比跑到第 3 分钟被 `⏱ 任务卡住了` 掐掉）。

**决定**：
1. 用 `ToolStarted` / `ToolFinished` 维护 `tool_in_flight`；
2. 窗口分两档：模型阶段 180s，工具执行期间 **30 分钟**（`stall_limit()`）；
3. 兜底仍在：每个工具自带超时（`exec` 的 `timeout_ms`、`web_fetch` 30s），
   `delegate` 的子 agent 有自己的墙钟（`[agents] wall_ms`，0 = 不限，启动时会 warn）。

**非目标**：不给工具加通用心跳事件（要动事件流契约）；不做"按工具类型算预期时长"。

**代价**：真卡死的工具会拖到 30 分钟才收口。长任务本就应该走后台——后台任务不经过这道判定。

**验收**：
1. 前台 `delegate` 跑 10 分钟不再被 180s 判死；
2. 模型侧真卡住（无 delta、无工具）仍在 180s 收口；
3. 工具卡死最迟 30 分钟收口，并给出"卡住了"的说明。

## D39 · 多 provider：按 agent 选提供方，但只由主人配置（设计已定，未实现）

**背景**：`[engine]` 只能配一个提供方，主 agent 与所有子 agent 共用。换模型只能全局换，
而不同环节的诉求不一样（规划要强模型、批量抽取要便宜/长上下文的模型）。
2026-11-05 zai 的 coding 端点在 18k 级 prompt 上频繁首字超时/挂起，需要按角色分流。

**决定**：

1. **配置形态**：

   ```toml
   [engine]
   provider = "zai"              # 主 agent 的默认

   [providers.zai]
   kind = "zai"                  # 预设名：决定 base_url 与协议
   model = "glm-5.3-flash"
   api_key_file = "~/.config/chuan/secrets/zai_key"

   [providers.ocgo]
   kind = "opencode-go"
   model = "deepseek-v4.1-flash"
   api_key_file = "~/.config/chuan/secrets/opencode_go_key"
   ```

   旧写法（只有 `[engine] provider/model/base_url/api_key_file`）在加载时**自动合成**一个
   同 id 的 provider，老配置无需改动。

2. **解析顺序**（主与子一致）：`profile → 角色（[agents.roles.<name>] / roles/<name>.toml）→ [engine].provider`。
   子 agent 想换提供方，就在角色里写 `provider` + `model`。

3. **只读可见**：`role list` / `role show` 会列出可用 provider 的 `id · kind · 默认 model`——
   **不含路径、不含密钥**。`role add provider="<id>"` 校验 id 是否存在，不存在就报错并列出可选项。
   这样父 agent 在创建/编辑子 agent 时"看得到能选什么"，但改不了 provider 本身。

4. **provider 只能由主人配置**：agent（含 `role` 工具）不能新增、修改或删除 provider。
   这与 `service` 的"运行时热加"**明确不同**——provider 是带凭据的出网通道，能加就等于能开新出口。

5. **密钥**：每个 provider 一个文件（`0440 root:chuan`），由服务进程直接读取；
   不进上下文、不进日志、不写进角色文件（角色里只存 provider id）。沙盒永远看不到 secrets。

6. **切换是手工的**：改 `[engine].provider` 或角色的 `provider` 后重启/热加载角色；
   v1 **不做**运行期 `/provider` 切换命令。

7. **记账**：`usage.recorded` 增加 `provider` 字段；`usage_rollup.model` 存 `provider/model`，
   便于按提供方拆账。

**非目标（v1）**：运行期切换；agent 自建 provider；每个 provider 独立的超时/重试
（先沿用全局 `[engine] max_retries` 与首字/空闲超时）；非 OpenAI 兼容协议（新增厂商仍需加预设代码）。

**验收**：

1. 只有 `[engine]` 的老配置无需改动即可启动，行为不变；
2. `[agents.roles.coder] provider = "ocgo"` 后，coder 的请求确实走另一家（`usage_rollup` 可见）；
3. `role list` 输出包含可用 provider 且不含任何密钥路径；`role add provider="nope"` 报错并列出可选项；
4. 未知 provider 在**启动时**报配置错误（退出码 2），不是等到第一次调用；
5. secrets 路径不出现在 system prompt、工具输出、日志中。

## D40 · 上传也走服务工具（`upload_from`），但请求头由宿主限定

**背景**：alist 的 `PUT /api/fs/put` 需要把文件本体当请求体，并且**目标路径在头里**
（`File-Path: <urlencoded>`）。`body_file` 帮不上忙：它限 1MB、强制 `application/json`，
而且是给脚本生成的小 JSON 用的。于是 agent 只能走 `host` lane + curl——那要审批、会把 token
带到命令行与 journald，正是 D9/D14 要避免的。

**决定**：`http` 增加 `upload_from`（`/ws` 下的相对路径，PUT/POST）与 `headers`
（原样发送的请求头）。实现要点：

1. **流式**：`ReaderStream` + 显式 `Content-Length`，不把整份文件读进内存
   （单板机 `MemoryMax=1G`，512MB 上限不能靠 buffer 兜）；上限与下载一致，512MB。
2. **走 transfer client**：与下载同一个"不设总超时、只设空闲超时"的 client，
   否则上传大文件会被 30 秒总时限腰斩。
3. **请求头白名单**：`authorization` / `cookie` / `proxy-authorization` / `host` /
   `content-length` / `transfer-encoding` / `connection` 一律拒绝；值是字面量、不做
   `{token}` 渲染。鉴权仍只由 `token_file` 注入。
4. 与 `save_to` / `body` / `body_file` 互斥；`upload_from` 走 `/ws` 同一条越界检查。

**为什么不是"任意 URL 上传"**：和下载一样，域名只来自服务配置，模型给的是 path 与文件名。
所以没有新增 SSRF/外泄面，`outbound` 域照旧免问。

**非目标**：断点续传；分片上传协议（各家的 multipart 语义不同，交给 playbook 与上游 SDK 的
HTTP 形态，内核只做"一个有头的 PUT"）。

**验收**：
1. `/ws` 下 200KB 文件经 `upload_from` 发出后，服务端收到的字节与文件一致、`Content-Length` 正确；
2. 自定义头（如 `File-Path`）确实到达；`Content-Type` 缺省是 `application/octet-stream`；
3. `headers` 里写 `Authorization` / `Content-Length` / `Host` → `InvalidArgs`，不发请求；
4. 与 `save_to`、`body`、`body_file` 同时用 → `InvalidArgs`；`upload_from` 越出 `/ws` → `InvalidArgs`；
5. 总耗时超过 API 总超时的上传仍能完成（与下载同一条 transfer client）。

**反悔成本**：低。删掉 `upload_from` / `headers` 两个参数即回到"只能取、不能写"。
